# Agent definitions (gap 1, the local part) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans
> (inline, test-driven). Steps use checkbox (`- [ ]`) syntax.

**Goal:** an agent is a file `agents/NAME.md` (a header like a skill's,
the instructions as its body); a run is one execution of it. Built-in
`main` and `helper` reproduce 0.3, so without `agents/` nothing changes.
`delegate` names a definition, the owner picks one per conversation
(`/agent NAME`) or per message (`/ask NAME text`), a context is kept per
{definition, conversation}, and an agent may propose a new definition or
a change to its own with `agent_save`, asked every time, shown in full,
what widens first.

**Spec:** `docs/superpowers/specs/2026-11-22-harness-agents-design.md`
under the binding overview
`docs/superpowers/specs/2026-11-22-harness-platform-overview.md`. Phase 0
(who, rules sections, grants with who, the `agent_save` kind asked every
time) and gap 4 (conversations, contexts per conversation, `send`) are
in. The hosted note is design only: no code for it.

**Architecture:** a new `agents.zig` reads, checks and keeps the
definitions (`Def`, `Set`), with the built-ins as texts that `harness
init` writes and the same parser reads; it also compares two versions
(what widens). `agent.zig`'s `Run` carries its definition (a copy taken
when it starts), and its tools, prompt, memory, skills, model and limits
come from it; `delegate` resolves each task's definition; `agent_save` is
a tool there. `core.zig` loads the set with the settings, keys contexts
by {definition, conversation}, queues each message with its definition,
and has the commands. `skills.zig` lends its header reader.

**Tech:** Zig 0.17.1, std only. `zig build test` (unit, then
`scripts/smoke.sh`); `-Dtest-filter=NAME`; `zig build unit` for unit only.

## Rulings

Where the spec can't work as written, the smallest change that keeps its
intent (what – why – cost if wrong):

- R1. Instances take turns in the one chat queue: one owner turn at a
  time, in arrival order, whatever the definition (each instance still
  has its own context and takes its inputs in order). – Running
  instances side by side needs a waiter per question (the inbox, gap 5,
  built in parallel, replaces today's single question and `ask_lock`);
  gap 4 left parallel turns out for the same reason. – A long turn of one
  definition delays the owner's message to another, as today across
  conversations; the inbox merge can give each instance its own worker.
- R2. The built-in `helper` has `tools: *`; a delegated task that names
  no tools gets 0.3's six (search, fetch, browse, read_file, recall,
  skill) when its definition is `helper`, else its definition's own
  tools. – In 0.3 `delegate`'s `tools` granted any tool but the excluded
  ones (owners and tests hand `shell` to helpers); with tools that only
  narrow, a helper limited to six could not get them. – `helper.md`
  reads `tools: *` although a bare task gets six; a comment in it says so.
- R3. `memory: pinned` decides what goes into the prompt; a `recall` tool
  the definition lists still searches memory. – 0.3's helpers read only
  pinned items in their prompt and have `recall` among their six. – A
  pinned definition that lists `recall` can look memory up.
- R4. `parallel`: an owner's turn always runs (it counts toward its
  definition's places, never waits for one); a scheduled run that finds
  no place runs at a later tick; a delegated run waits until its turn
  ends, and is refused at once when the run that delegated it holds its
  definition's only place. – "One place always kept for runs the owner
  started"; a run waiting for a place its own parent holds would wait out
  the turn. – While the owner talks to a definition, one more of its runs
  can be going than `parallel` says.
- R5. `saved:` in a file and the `saved` log line carry no item number
  until the inbox lands (`item` is null). – Items are gap 5's, built in
  parallel; today's questions have no id that reaches the run. – None
  beyond the missing number; the merge fills it.
- R6. A conversation whose definition is gone (`/agent rm`, or a file
  removed by hand and `/reload`) goes back to `main`, and the owner is
  told. – The spec refuses `rm` for one a task uses, not for one a
  conversation uses. – None.
- R7. `state/conversations` writes `"agent"` only when it is not `main`,
  at the end of the line. – Every line of a folder that uses no
  definitions stays as it was (an older harness reads them). – A reader
  must know that no `agent` means `main`.
- R8. A task's `agent =` must name a definition: checked at start and on
  `/reload`, naming the task. – `rm` is refused for a definition a task
  uses; the link holds both ways. – Removing a file by hand while a task
  names it stops `/reload` until the task is changed.
- R9. `/stop NAME` stops NAME's runs and the runs they delegated, and
  drops NAME's queued messages; a delegated run gets a stop flag of its
  own (set with its parent's) so it can be stopped alone. – Today helpers
  share their parent's flag. – None.

Made while building:

- R10. A question from a definition other than `main` and `helper` names
  it (`[researcher] shell: …`; a helper of it `[chat/h1 researcher] …`). –
  "24 h grants per definition, since every question names who asks"; 0.3's
  questions named only helpers. – None: main's and helper's read as before.
- R11. `delegate`'s `tools` takes what the model sees and what definitions
  write: built-in names, `server__tool`, `server/tool`, `server/*`, and
  `mcp` for every MCP tool (0.3 read only kind names, `mcp` among them). –
  Narrowing by name needs MCP tools by name. – None.
- R12. `tools: none` and `skills: none` say a definition gets none. – The
  key table has no way to say it, and an empty list reads as a mistake. –
  One word the parser takes beyond the spec.
- R13. A message's definition is fixed when it is queued; a turn whose
  definition is not the one answering in that conversation (an `/ask`, a
  press under such a post, a message queued before `/agent`) marks its
  posts `[NAME]`. – "/agent NAME uses NAME from the next message on". –
  None.

Notes:

- Existing tests changed on purpose: only
  `kinds_without_a_tool_yet_are_not_offered_or_run` (agent.zig) no longer
  lists `agent_save`, which has a tool now. `no_agents_folder_means_0_3`

- Left out: an app run's tools (gap 8; it starts like the owner's, passing

### Task 1: the definition format

**Files:** `src/skills.zig`, `src/agents.zig` (new), `src/main.zig` (test import)

```zig
// skills.zig
pub const Field = struct { key: []const u8, value: []const u8, line: usize, nested: bool = false };
pub const Header = struct { fields: []const Field, body: []const u8, closed_line: usize };
pub fn readHeader(arena, text) !Header; // `---` … `---`; block scalars, quotes, `#` lines skipped; error.NoFrontmatter
// agents.zig
pub const max_file = 8 * 1024; pub const max_defs = 32;
pub fn validName(name) bool;              // skills' rule, not list|show|rm
pub const Memory = enum { shared, pinned };
pub const Def = struct { name, description, model = "", tools: []const []const u8 = &default_tools,
    skills: []const []const u8 = &.{"*"}, memory = .shared, steps/tokens/seconds/answer_bytes: ?u32 = null,
    parallel: u32 = 0, environment = "host", saved = "", body = "", text = "", builtin = false;
    pub fn allowsTool(d, name) bool; pub fn allowsSkill(d, name) bool; pub fn clone(d, a) !Def };
pub const default_tools = [_][]const u8{ "search", "fetch", "browse", "read_file", "recall", "skill" };
pub const Diag = struct { file: []const u8 = "", line: usize = 0, why: []const u8 = "" ; pub fn text(d, a) ![]const u8 };
pub fn parse(a, name, text, diag: *Diag) error{ BadDefinition, OutOfMemory }!Def;
pub fn toolMatches(patterns, name) bool;  // "*", NAME, "server/tool", "server/*", "*/*" (any MCP tool)
pub const main_md, helper_md; pub const builtin_main: Def; pub const builtin_helper: Def;
```

Keys: `name` (the file's), `description` (one line), `model`, `tools`
and `skills` (comma-separated; `none` for none), `memory`, `steps`,
`tokens`, `seconds`, `answer_bytes` (whole numbers from 1), `parallel`
(from 0), `environment` (`host` only until gap 2: "environment: only host
for now; other environments come later"), `saved` (harness's).

Tests:
- agents `bad_definitions_are_named_with_their_line`: name not the
  file's → line 2, "name researchr is not the file's name (researcher)";
  `colour: red` → its line, "unknown key colour"; `tools: search, telnet`
  → "unknown tool telnet"; `environment: box` → "only host"; a key given
  twice; a nested line; 8193 bytes → line 0 "over 8 KB"; no closing `---`.
- agents `a_definition_reads_every_key`: the spec's example reads back
  (tools with `github/list_issues`, memory pinned, parallel 4), and
  `allowsTool` takes `github/list_issues`, not `github/create_issue`;
  `server/*` takes all of a server's; `*` all.
- agents `the_builtins_read_as_their_files`: `parse(main_md)` equals
  `builtin_main` field by field (tools `*`, memory shared), same for
  helper (tools `*`, memory pinned); `validName` refuses `rm`, `Main`.
- skills tests pass unchanged (the reader is shared).

## Review Focus

- No definition widens its own tools, model, memory or environment
  without the owner: `agent_save` is asked every time (no grant or allow
  rule lifts it), never offered unattended or to delegated runs, and only
  for a new definition or the run's own; no tool writes `rules`.
- A run's tools never exceed its starter's: every check goes through the
  definition, the narrowing and the starter's own `allows`.
- Without `agents/` (or with init's two files) behaviour is 0.3: the same
  tools, limits, models and memory for the chat, tasks and helpers.
- A run keeps the definition copy it started with; `Set.save` swaps under
  its mutex and frees nothing a run holds.
- Every new Core field is set in `Core.open`; the set is freed in close.
