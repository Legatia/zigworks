# Triggers (gap 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans
> (inline, test-driven). Steps use checkbox (`- [ ]`) syntax.

**Goal:** A trigger is an event source with a filter; a match starts a
run, a message or (once gap 7 lands) a workflow. One parser reads
`tasks.ini`, `briefs.ini` and the new `triggers.ini`; tasks and briefs
are two kinds of trigger and keep working unchanged. Event kinds now:
feed, search, page, file, mcp (resource or tool). State is on disk
first (`state/triggers/NAME/`), polls pass the gate as listed reads,
runs are unattended (`trigger:NAME`), limits hold storms, the agent's
`trigger add` is a setup call asked every time with harness's reading.

**Spec:** `docs/superpowers/specs/2026-11-22-harness-triggers-design.md`
under the binding overview
`docs/superpowers/specs/2026-11-22-harness-platform-overview.md`. In
already: phase 0 (who `trigger:NAME`, gate kind `trigger`, nobody can
answer for trigger runs), conversations (`runIn`, `RunOut{tag, sched}`,
a `to` opens its topic at the first post), inbox (`addItem`,
`agent.Keeper`, `answerItem`), agent definitions (`agent =`,
`useDefinition`, `run.narrow`, places), providers (`modelClient`).

**Not now** (the owner hasn't decided): the `mail` kind (left out
entirely: `mail =` is an unknown key); money from trigger-started runs
(refused behind `[money] triggers = off`; `on` follows `[money]
scheduled` and a cap as the spec says); `start = workflow NAME` is read
and refused at its events with "workflows aren't built yet" in one
function gap 7 replaces. Webhooks and websockets stay in the spec's
Later.

**Architecture:** three new transport-free files and the engine in core.

- `src/triggers.zig`: the one format (sections of the three files, a
  section's keys give its kind), the name rule, filters (`match`,
  `skip`; workflows' `if` shares them), `say` placeholders, next-poll
  times, harness's own reading of a trigger.
- `src/tstate.zig`: `state/triggers/NAME/`: `state` (JSON, temp file
  then rename), `seen` (`brief.Seen`, 60 days), `queue` (JSON lines
  appended: events, `checked`, `started`, `done`; compacted when all
  are done or past 1 MB), `last` (a page's last readable text).
- `src/sources.zig`: what each kind reads, through a `Decider` (listed
  for polls, the chat run's own gate for the tool's `test`), and what
  is new against the state: feed, search, page (ETag, Last-Modified,
  304, `json` path, `value`/`change`/`move`, lines added and removed),
  file (two stable polls), mcp (resource, tool).
- `src/core.zig`: the trigger list (its own arena, swapped at once by
  `/trigger add|rm` and the tool), the poller (one thread at a time,
  spawned by `tick`), the queue and limits, action jobs in the
  background slots (say, do, start), checks, pause and its inbox item,
  commands, the tool's desk, workflow hooks.
- `src/agent.zig`: the `trigger` tool (offered only in owner-started
  conversation runs), the money setting, no `write_file` where a file
  trigger watches.

**Tech:** Zig 0.17.1, std only. From `harness/`:
`zig build test --summary all --cache-dir DIR` (unit, then smoke);
`-Dtest-filter=NAME` for one test.

## Global constraints

- Copy: plain labels, no slogans. Posts carry `[NAME] ` like tasks.
- Every new Core field is set in `Core.open` (it sets `c.* = undefined`).
  No `trig_mutex`, `settings_mutex` or inbox lock held across a network,
  model or channel call.
- Secrets never in model requests, logs, items, the queue or test
  output: events are masked against the mask list when found.
- State before acting: a poll appends its events to `queue` before
  `state` and `seen` move; a run's events are marked `started` before
  it runs and `done` after its answer was posted or kept.
- Old `tasks.ini` and `briefs.ini` read exactly as before; `ran` and
  `paused` keep their keys; existing tests change only where listed in
  Notes.
- macOS, Linux, Windows: file polls use stat, patterns ignore case on
  macOS and Windows; nothing refused on any platform.

## Rulings

What – why – cost if wrong:

- R1. The name rule (phase 0 ruling 3): a name is 1–64 of a-z, 0-9, `-`
  and `_`, starting with a letter or digit, and none of the commands'
  words (`add`, `rm`, `pause`, `resume`, `run`, `test`, `list`,
  `show`). The one parser enforces it in `triggers.ini` (a bad line)
  and `/task add` refuses a new task breaking it; a name in
  `tasks.ini` or `briefs.ini` that breaks it still loads, its `by`
  written as is (phase 0), and `/triggers` marks it ("rename it to name
  it in rules and grants"). A `triggers.ini` name may not repeat any
  name of the three files; a task and a brief sharing a name, as 0.3
  allowed, still load. – Old files must keep working; new ones get
  names rules and grants can hold. – An owner with such a name sees a
  mark in `/triggers` until they rename it.
- R2. `max_runs` and `[triggers] runs_per_hour`/`runs_per_day` count
  `do` runs; a `say` is a message, held like every post by
  `sends_per_hour`. – A `say` costs nothing and the spec's btc example
  polls every 5 minutes. – A chatty `say` trigger posts up to 60 an
  hour per conversation.
- R3. A trigger's `check` runs in its action job (a background slot),
  not on the poll thread. – Polls make no model call; checks and runs
  share the slots tasks use. – Checks wait for a free slot like runs.
- R4. A poll is logged as a run labelled `poll NAME`, `by` `trigger:NAME`,
  no definition (`agent` ""), so its gate lines carry a `rid`; a call
  with no definition matches no `agent:` pattern in rules or grants
  (`who.reach`). – Rule 1 wants every read logged; a poll is no
  definition's. – `harness log runs` lists polls.
- R5. `/trigger add|rm`, the tool's `add`/`rm` and a paused item's
  Remove apply at once by swapping only the trigger list (its own
  arena); other files and hand edits of `triggers.ini` still wait for
  `/reload`. The settings watcher keeps a hash per file. – "`/trigger
  add|rm` at once" while `/reload` refuses while anything runs. – None
  known.
- R6. A role refusal of a file trigger's read (folders.ini) pauses it;
  other failed polls back off. – It does not mend itself. – One pause
  item to Resume after editing folders.ini.
- R7. Events of a trigger with `start = workflow NAME` are done
  (logged `dropped`, "workflows aren't built yet") and the owner is
  told once per trigger, until gap 7 replaces `startWorkflow`. –
  Instruction. – Events found meanwhile are lost.
- R8. `/trigger run NAME` and `harness trigger run NAME` poll at once
  and act on what is queued, outside `max_runs` (by hand, as `/brief`
  ignores its time). – The owner asked for it now. – None.
- R9. A trigger's undelivered answer (a delivery item) does not block
  the trigger: its events are done and the item is sent again on its
  own. – Spec: done once posted or kept. – None.
- R10. `change` and `move` count from `base`: the value of the last
  event acted on (said, run or started), or the first poll's value. –
  Spec: "since the last run or message". – None.

Made while building:

- R11. In triggers.ini only whole lines are comments (`;` or `#` first);
  a `;` or `#` inside a value is kept (`say = PR #{number}`). tasks.ini
  and briefs.ini keep config.ini's rule (also after a space). – Free text
  in `say`, `do` and `check` holds them, and the old rule cut `say = PR
  #{number}` silently to "PR". – An inline comment in triggers.ini is
  part of its value (where a value is checked, its line is named).
- R12. A subscribed MCP resource is also read every `every` (15 min by
  default), not only when its server says it changed. – The read is
  listed and cheap; a lost notification (a server restart) is then not
  missed for long. – A read every 15 minutes.
- R13. Only `harness run` and `harness chat` poll (`Core.poller_on`);
  one-off commands do not, and `harness trigger run NAME` polls the one
  named. Tests poll by hand (`pollNow`). – A `task run` must not start
  unrelated polls. – None.
- R14. A pause stops polls; queued events are still acted on (so a full
  queue drains before Resume), except `do` runs after a spent budget,
  which wait for Resume. – Else a full queue paused for good. – None.
- R15. `/stop` during a trigger's run marks its events done ("stopped by
  the owner"); a stop because harness ends keeps them for the run after
  the restart, which is told so. – The owner stopped that run; a restart
  must not lose events. – A stopped run's events are not tried again.
- R16. A changed page value's event id is its previous value, new value
  and base; a changed text's, its previous and new hashes. – The same
  change found again after a stop is queued once; a later repeat is new. –
  None.
- R17. A poll's who is `trigger:NAME` with no definition, so in
  folders.ini a file trigger's folder lists `trigger:NAME` (or `trigger`)
  for `read`. – Its read is harness's, for that trigger. – None.
- R18. The `[money] triggers` check comes before the gate's money
  decision: refused naming the setting, not kept as a skipped item (no
  approval lifts it). – Instruction (owner question 2). – None.
- R19. `/trigger pause|resume` take triggers.ini's entries (a schedule or
  brief of it pauses through `state/paused`, as tasks do); tasks keep
  `/task resume`. `/trigger rm` removes only triggers.ini's sections and
  says where a task or brief is. – Tasks and briefs stay in their files.
  – None.
- R20. The tool's `test` of a trigger never polled reads what is there
  as if it were new (a file trigger's first poll lists its files). –
  "What would start" is empty on a first poll otherwise. – None.

### Task 1: one format for the three files

**Files:** `src/triggers.zig` (new), `src/config.zig`, `src/main.zig`
(test import)

```zig

pub const Op = enum { has, is, starts, ends, like, gt, lt, ge, le };
pub const Cond = struct { field: []const u8, op: Op, values: []const []const u8 };
pub const Field = struct { name: []const u8, value: []const u8 };

pub const Trigger = struct { name, file: File, kind: Kind, line: usize, name_ok: bool = true,
    every_s: ?u32 = null, at: ?u16 = null, days: u7 = 0x7f,
    sources: []const []const u8 = &.{}, json: []const u8 = "", mcp: ?Mcp = null, key: []const u8 = "id",
    topics: []const config.Topic = &.{}, match: []const Cond = &.{}, skip: []const Cond = &.{},
    check: []const u8 = "", action: Action = .none, agent: []const u8 = "main",
    tools: ?[]const []const u8 = null, to: []const u8 = "main",
    max_runs: u32 = 6, max_events: u32 = 20, checks_per_day: u32 = 50,
    added: []const u8 = "",       // "added by agent:main 2026-11-22 (item 41)"
    first: usize = 0, last: usize = 0, // its lines in the file, the mark above the header included
    pub fn clone(t: Trigger, a: Allocator) !Trigger;
    pub fn isEvent(t: Trigger) bool; };
pub const Diag = struct { line: usize = 0, why: []const u8 = "" };
pub fn parse(a: Allocator, text: []const u8, file: File, diag: *Diag) error{ BadTrigger, OutOfMemory }![]Trigger;
pub fn validName(name: []const u8) bool;
pub fn fieldsOf(kind: Kind) ?[]const []const u8;      // null: any (mcp)
pub fn parseCond(a: Allocator, text: []const u8, kind: ?Kind) !Cond;
pub fn holds(c: Cond, fields: []const Field) bool;
pub fn passes(t: Trigger, fields: []const Field) bool; // every match holds, no skip holds
pub fn fill(a: Allocator, template: []const u8, fields: []const Field) ![]const u8; // {change} signed, one decimal
pub fn nextPoll(t: Trigger, after: i64, utc_offset: i32, jitter: u32) i64;
pub fn reading(a: Allocator, t: Trigger, check_model: []const u8) ![]const u8;

```

- `tasks.ini` takes at/every/days/do/to/agent and `briefs.ini`
  at/to/topic exactly as today (one entry per run of a section name,
  a name again later is an error, a header with no keys no entry);
  their errors are `BadConfig` for `parseTasks`/`parseBriefs`.
- `triggers.ini`: source keys `topic`, `feed`, `search`, `page`, `file`,
  `mcp` give the kind (none: schedule; two kinds: bad line); event
  kinds take `every` (`30s`, `5m`, `1h`, `1d`; least feed/page 5m,
  search 1h, file 30s, mcp 1m; default feed/page 1h, search 6h, file
  1m, mcp 15m) or `at`, `days`, `match`, `skip`, `check`, one of
  `do`/`say`/`start`, `agent`, `tools`, `to`, `max_runs`, `max_events`,
  `checks_per_day`; `json` (page), `key` (mcp tool); a schedule needs
  one of `do`/`say`/`start` and one of `every` (minutes, ≥ 5m)/`at`.
  Filter fields and `{field}` names are checked against the kind's
  fields (`feed`: title, link, text, date, source; `search`: title,
  link, date; `page`: text, removed, value, change, move; `file`: path,
  change, size; mcp: any). `start` is `workflow NAME`. `file =
  FOLDER/PATTERN`: relative, no `..`, `*` only in the last part.
  `mcp = SERVER resource URI` or `SERVER/TOOL {json object}`.
- `[triggers]` in config.ini: `check_model` (default "": `worker_model`),
  `checks_per_day = 200`, `runs_per_hour = 20`, `runs_per_day = 100`,
  `queue = 200`; `[money] triggers = off`; both in `defaults_ini`.
- `config.Task` gains `say`, `start` (workflow), `from: triggers.File`;
  `Task.clone`, `Brief.clone`. `feeds.Entry.text` (description,
  summary or content, as text).

Tests (triggers.zig unless named):
