# The car's heating: carcloud's Tesla backend, the warm-car routine, calmcp refusing unknown fields (section 7 of the household spec) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Tesla owner's car warms before a cold morning's leave-by with one tap. carcloud gains `backend = tesla`: the owner's own Tesla developer application signs in once (`carcloud login`), `car_status` reads Fleet API `vehicle_data`, and the commands the car file allows (`car_command`'s charging and lock, `car_climate` on/off/temperature within `climate_temp`, `car_seat_heat`) go through Tesla's signed-command path, rate-limited, daily-capped, logged and read back. harness's `warm-car` routine asks "Warm the car for 8:10?" [Warm it] 30 minutes before a morning leave-by when the car reads below `[butler] warm_below = 5` °C outside; only the tap makes the call. calmcp refuses tool fields it doesn't know.

**Architecture:** carcloud: `config.zig` reads `backend`, the Tesla keys and the new allow words; `tesla.zig` (OAuth code exchange and rotating refresh token, Fleet API reads and wake, commands to the signing proxy, the status lines and read-backs); `server.zig` keeps Smartcar's paths as they are and dispatches to a backend; `http.zig` trusts one extra CA file per client (the proxy's certificate), its unused "accept any certificate" switch removed; `carcloud-sim tesla DIR` plays Tesla's auth, the Fleet API and tesla-http-proxy (TLS, a CA made at start: mailmcp's `testca.zig` and `tlsserver.zig`, sim only). harness: `examples/butler/workflows/warm-car.wf` (approve with `yes Warm it`, then `car/car_climate {"state": "on"}`), `butler.Routine.@"warm-car"` offered when the car server has `car_climate`, `[butler] warm_below`, and one core hook beside the diary (`warmCarDue`): before a morning leave-by it reads `car/car_status` (waking the car once), and below the threshold starts the instance as `schedule:warm-car`, a built-in schedule `workflows.check` accepts. calmcp: one check before each tool's dispatch against the tool's own field list.

**Tech Stack:** Zig 0.17.1, std only; macOS, Linux, Windows.

**Spec:** `docs/superpowers/specs/2026-11-23-harness-butler-household-design.md` section 7; `2026-11-23-harness-butler-design.md` (UX rules: plain, one tap, read back, quiet); `harness/research/agent-beside-the-car.md` (Fleet API, tesla-http-proxy, virtual key, costs).

## Review Focus

### Commands only within the car file's allowlist and limits

1. **Nothing the car file doesn't list is sent.** `car_climate` and `car_seat_heat` exist only when `allow` lists `climate` and `seat_heat`; the server refuses them otherwise (a tool name the list doesn't have is "no tool called"). There is no pass-through: each tool maps to fixed Fleet API command names (`auto_conditioning_start/stop`, `set_temps`, `remote_seat_heater_request`, `charge_start/stop`, `set_charge_limit`, `door_lock`, `door_unlock` only as `car_unlock`). (`tesla_tools_follow_the_allow_list`, smoke "only allowed tools".)
2. **Limits.** A temperature outside `climate_temp` (within Tesla's 15–28 °C) is refused before anything is sent; a seat or level outside the fixed names and 0–3 too; every command, Tesla's too, counts against `commands_per_day` and `min_seconds_between`; a wake for reading counts against `wakes_per_day`. Refusals are logged. (`climate_limits_are_read_from_the_car_file`, smoke "a temperature outside the owner's range", "the day's cap".)
3. **Unknown fields refused** by the new tools (a misspelt field would otherwise go unnoticed): `car_climate {"state":"on","temp":30}` is refused, nothing sent. (smoke.)
4. **Smartcar can't be asked for climate.** `climate` or `seat_heat` in a Smartcar car file is a bad line. (`a_smartcar_file_refuses_climate`.)
5. **harness: the owner's tap makes the call.** The routine's call is fixed in the file (`yes` already refuses a `{value}` in the next step's input); without the tap (Not today, the question lapsing at leave-by) nothing is called; the hook starts nothing for a warm morning, an afternoon, a leave-by already asked about, or with the routine off. (`warm_car_asks_before_a_cold_morning_leave_by_and_one_tap_warms`, `warm_car_stays_quiet_when_it_is_warm_afternoon_or_off`.)

### Secrets

1. The refresh token lives only in the token file (owner-only, replaced whole); the access token in memory; the client secret only in `carcloud login`'s environment (and in a refresh when set). None is printed, logged or put in an error. (`the_token_file_is_owner_only_and_replaced_whole`, smoke "no token in any output".)

## Rulings

(Each: what – why – cost if wrong.)

1. **Signed commands go through Tesla's `tesla-http-proxy` sidecar.** What: carcloud sends command REST calls to `command_api` (the proxy, on loopback, HTTPS with its own certificate, trusted through `command_ca`); the proxy signs them with the application's key (the virtual key the owner paired once) and sends them to the car. Why: Zig std has the primitives (P-256 ECDH, HMAC-SHA256, AES-GCM, SHA-1), but the vehicle command protocol (protobuf routable messages, per-domain sessions with epochs, counters and clock offsets, two signature schemes) is specified only by Tesla's Go code; with no car to try, a Zig signer could only be tested against itself, and a mistake shows only as refusals on a real car. The research recommends the sidecar. Cost if wrong: the owner runs one more process (Tesla's own); a native signer can replace `command_api` later without changing a tool.
2. **Reads go to the Fleet API directly** (`api`), not through the proxy. Why: reading needs no signature; status keeps working with the sidecar down. Cost if wrong: two addresses in the car file.
3. **Sign-in: `carcloud login CAR.ini`**, authorization code with the owner's own application: `client_id` in the car file (not secret, as for Smartcar), the secret from `TESLA_CLIENT_SECRET`; the link printed, the address the browser ended on pasted back (its `state` checked); no listener. Why: works with any redirect URI the owner registered, no port opened. Cost if wrong: one copy and paste at setup.
4. **The refresh token is kept in `token =`** (default `CARFILE.token`, beside the car file), owner-only, replaced whole each time Tesla returns a new one (Tesla's refresh tokens rotate); the access token in memory until a minute before it expires (as Smartcar's). The running server needs no secret: Tesla's refresh takes the client id; `TESLA_CLIENT_SECRET` is added when set. Why: a rotated token must survive a restart; the environment can't be written back. Cost if wrong: two carcloud processes refreshing at the same moment can leave one with a used token: `carcloud login` again.
5. **`car_status` never wakes the car unless asked**: `{"wake": true}` wakes it (up to `wakes_per_day`, default 3, logged); asleep and not asked, it says so. Why: a Fleet API read of a sleeping car fails; each wake costs money and battery. warm-car needs a fresh outside temperature. Cost if wrong: the model may spend the day's wakes on its own (the cap holds it).
6. **A command wakes the car first** when asleep (`wake_up`, then the car's state every 3 s, up to 60 s), as part of that command (not a counted wake). Cost if wrong: a car that doesn't wake fails after 60 s with that reason.
7. **Read back** after each command: the proxy's `result: true` is the car's own acceptance; carcloud then reads `vehicle_data` and answers with what the car reports ("Climate on, set to 21 °C; inside 4 °C, outside -3 °C."). Not shown as asked: said so, not an error. Cost if wrong: one more read per command.
8. **Tools.** `car_climate {"state": "on"|"off", "temperature": °C}` (allow word `climate`; temperature in `climate_temp`, default 18–24, within Tesla's 15–28; with `on` and a temperature, `set_temps` then `auto_conditioning_start`, one counted command); `car_seat_heat {"seat": front_left|front_right|rear_left|rear_center|rear_right, "level": 0–3}` (allow word `seat_heat`; Tesla's `heater` numbers 0, 1, 2, 4, 5). Tesla also takes `car_command`'s commands (`charge_start`, `charge_stop`, `charge_limit`, `lock`; `unlock` only as `car_unlock`). Why: separate tools appear only when allowed and stay simple for a model. Cost if wrong: a seat named by side in a right-hand-drive car (front_right is the driver there; the README says so).
9. **Region.** `region = eu | na | cn` sets the Fleet API address and the token's audience; `api`, `auth_url`, `token_url` override (carcloud-sim). Cost if wrong: a wrong region is Tesla's 421, said plainly.
10. **Certificates.** The command endpoint's certificate is checked against `command_ca` only (the proxy's own certificate; the host name too, its CN when it has no SAN); without `command_ca`, the system's roots. carcloud's `http.zig` loses its unused "accept any certificate" field. Cost if wrong: an owner whose proxy certificate names another host gets "certificate was not accepted" (the README shows the openssl line with `localhost`).
11. **carcloud-sim tesla DIR** serves auth and the Fleet API over HTTP on 127.0.0.1 (as the Smartcar stand-in) and the proxy over TLS with a CA it makes at start; writes `ca.pem`, `car.ini`, `ports`. The Fleet API refuses unsigned commands (as Tesla's does for current cars), so a command that skipped the proxy fails the smoke. Cost if wrong: none for users.
12. **`carcloud check`** for Tesla: the sign-in (a refresh), the car's state without waking it, `vehicle_data` when awake, the virtual key (Fleet API `fleet_status`: paired or not) and the proxy (its certificate accepted). Exit 1 when the sign-in, the proxy or the car's read fails. Cost if wrong: none found.
13. **warm-car's timing.** The question comes 30 minutes before a leave-by (the diary's: the event's start less `[butler] travel` or the maps' minutes) whose time is before noon (the owner's time), once per event (a key in `state/diary`); [Warm it] lapses at the leave-by (`timeout 30m`). Why: Tesla's own preconditioning takes 15–30 minutes; the spec says morning. Cost if wrong: a 07:00 leave-by inside quiet hours: the question is held like any routine's (the README says so).
14. **Cold is the car's own outside reading**, from `car/car_status {"wake": true}` (one wake per morning leave-by), below `[butler] warm_below` (default 5 °C); no reading (car unreachable, Smartcar, no outside line), no question. Why: harness has no weather source of its own; the car's thermometer is where the car is. Cost if wrong: a car parked in a warm garage on a frosty morning isn't offered (the reading is the garage's).
15. **Started as `schedule:warm-car`**, a built-in schedule: the workflow's start line names it, `workflows.check` accepts it without a triggers.ini section, the routine adds no trigger. Why: the diary isn't a trigger source; `schedule:` is unattended (quiet hours, the inbox) as a routine's start should be. Cost if wrong: one name harness keeps for itself.
16. **Offered when the car can warm**: `/setup routines` offers warm-car when the car server (`car`) runs and lists `car_climate`. Cost if wrong: a car file without `climate` isn't offered (right).
17. **calmcp refuses unknown fields**: a tool call whose arguments hold a key its schema doesn't list is refused ("cal_create has no field location: it takes calendar, title, start, end, minutes, all_day, place, notes"), nothing read or written, a write tool's refusal logged; arguments that aren't an object too. Cost if wrong: a client that sends extra keys (none found in harness) gets an error.
