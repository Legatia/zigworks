# Inbox (gap 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans
> (inline, test-driven). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Everything that waits for the owner is an item in
`state/inbox`, written before anyone acts on it: approvals, the agent's
questions and drafts (`ask_owner`), calls an unattended run skipped,
posts that did not get through. Several are open at once, each answered
once (buttons, a text reply, `/answer`, the terminal), in any order; a
skipped call can be allowed for its task; undelivered posts survive a
restart.

**Spec:** `docs/superpowers/specs/2026-11-22-harness-inbox-design.md`
under the binding overview
`docs/superpowers/specs/2026-11-22-harness-platform-overview.md`. Phase 0
(`Decision.allow_day`, `Grants.addFor`, `Who`) and conversations
(`ChatAsk.conv`, `RunOut`, `Undelivered`, the `r` and `a` button letters)
are in.

**Architecture:** a new transport-free `inbox.zig` owns the item: its
fields, the file (a first line with the next id, then a JSON line per
item, temporary file then rename), format v1, retention, the private
form, and the texts harness shows (message parts, outcomes, list lines,
button data). Core owns the rest: making items, showing them in a
conversation, presses, text answers, the one answer function, waiting
runs, expiry, restart, skipped items and their task grants, deliveries
and their retries, `/inbox`, `/answer`, `/grants`, the reminder.
`agent.zig` asks through the `Asker` (now returning a `Reply`), owns the
`ask_owner` tool, and hands skipped calls to a `Keeper`.

**Tech:** Zig 0.17.1, std only. From `harness/`:
`zig build test --summary all --cache-dir DIR` (unit, then smoke);
`-Dtest-filter=NAME` for one test.

## Global constraints

- Copy: plain labels, no slogans. Message heads as the spec writes them:
  `Allow this? [41]`, `Question [44]`, `Draft to review [46]`,
  `Skipped [45]: task btc-watch could not make this call without you:`,
  `Not delivered [52] …`; helpers' items keep `[chat/h2]` in the body.
- Button data `i<id>-<token>:<key>` (≤ 64 bytes), token 16 hex per item;
  `s<id>` for Show; `a` (old approvals) is out of date; `r` stays quick
  replies.
- `title` ≤ 200 bytes, `body` ≤ 12 KB; both masked with the instance's
  mask list; a private run's item keeps its texts while open, only size
  and keyed hash once closed.
- `state/inbox` rewritten whole under one lock on every change, before
  a waiter is told; open items and those closed in the last 7 days, at
  most 500; at most `[inbox] questions` (20) run items open; other kinds
  at most 200 open (past that the oldest skipped expire).
- Every new Core field is set in `Core.open` (it sets `c.* = undefined`).
  No inbox lock held across a channel call, `c.lock` or `convs.mutex`.
- Secrets never in model requests, logs, items or test output.
- macOS, Linux, Windows (tests use `type` for `cat` there).

## Rulings

What – why – cost if wrong:

- R1. `state/inbox` starts with `{"next":N,"reminded":D}`: the next id
  and the local day the reminder last went out; `state/approvals` gives
  the first id when there is no `state/inbox`, and is deleted once
  `state/inbox` is written. – Ids must not come back once closed items
  age out, and "once a day" must hold across a restart. – A reader of the
  raw file skips one line; `harness inbox` and apps read through harness.
- R2. A closed private item's `title`, `body`, `draft`, answer `text` and
  a delivery's text become the log's private form `{"bytes":N,"hmac":"…"}`,
  in the file and in format v1. – "Only size and keyed hash" does not fit
  in a string. – Apps must accept an object in those fields of a closed
  private item.
- R3. The message is the item: a stored secret in a call shows as
  `[secret:NAME]` in Telegram and the terminal too. – Items pass the mask
  list. – The owner approves a call whose secret they see by name.
- R4. An item of a run that reports to a conversation others read (a
  task's `to` naming a group) is shown in `main`. – Its text and buttons
  are the owner's. – None known.
- R5. `ask_owner` has no `app` until gap 8; items carry `"app":null`. –
  There is no app to name yet. – Gap 8 adds the property.
- R6. A delivery item keeps a post's text and a brief's links, not its
  files or quick replies; the run is told which files did not go. – Files
  are workspace data, quick replies need their run. – A failed post is
  sent again without them.
- R7. A delivery being retried blocks its brief or task until it is
  delivered, dropped or expires (7 days); one that failed for a reason
  not worth trying again (not paired, no channel) is posted for the owner
  and its brief or task counts as run, as today. – Else a brief whose
  item the owner ignores never runs again. – None known.
- R8. `/stop`, a signal and leaving `harness chat` withdraw the waiting
  run items; the agent is told "stopped by the owner" or "withdrawn: no
  one is left to answer", not "denied by the owner". – The owner did not
  deny. – `closing_the_terminal_denies_the_question_and_any_after_it`
  changes. Items are void at start only when their process died without
  closing them (a crash).
- R9. `/inbox` lists the oldest 20 open items with Show buttons, then
  "And N more: harness inbox lists them all." – A message holds 4,096
  bytes and Telegram ~100 buttons. – The 21st needs `harness inbox`.
- R10. Keyboards: up to 3 buttons on one row, 4 as two rows of two, more
  in rows of four (quick replies with four labels too). – The spec's
  "one row (two for four choices)", one rule for every keyboard.
- R11. A skipped call of a task whose name is not a who value (phase 0
  let names with a space stand) offers no "Allow for this task". – A
  grant's `who` must be a value. – Rename the task to get the offer.

### Task 5: `ask_owner`

**Files:** `src/agent.zig`, `src/core.zig`

- Tool `ask_owner` `{question, choices?: ≤4 of 1–64 bytes, text?: bool,
  draft?: string}`; a question without choices takes text; a draft takes
  no choices; question + draft ≤ 12 KB. Gate kind `ask_owner`, argument
  the question. Offered only when `!helper and !scheduled and asker !=
  null`. Items: question (`1`…`4`, text `answer` when allowed), draft
  (`use` "Use it", `drop` "Drop", text `draft`). Results: `chose: Work`,
  `wrote: …`, `draft used as it is`, `draft replaced by the owner: …`,
  `dropped`, `no answer in time`.

Tests:
- `ask_owner_returns_the_choice_or_the_text` (core): choices
  Personal/Work → `Question [1]` with two buttons; press `2` → request
  has `chose: Work`; a text question answered by reply → `wrote: the
  blue one`.
- `a_draft_answered_with_text_returns_the_owners_version` (core): a
  reply → `draft replaced by the owner: Hi Anna, see you at 7.`; a second
  draft pressed `use` → `draft used as it is`.
- `ask_owner_is_not_offered_to_helpers_or_unattended_runs` (core): in a
