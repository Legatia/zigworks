# calmcp and the butler's diary (section 2 of the duties spec) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The butler keeps the owner's diary. calmcp, a new MCP server beside homemcp and carcloud, reads the owner's CalDAV calendars (iCloud, Fastmail, Nextcloud with an app password; Google with an OAuth token) and, in the calendars its file allows, creates, moves, cancels and answers invitations, each change read back. In harness, `/setup calendar` connects it in chat; the morning summary lists today's events; a line says when to leave for an event with a place; 30 minutes before a meeting with people, a short preparation (who, where, what was said with them last, the links); during a busy event, posts wait as in quiet hours; and a change the owner asks for is proposed and asked by the gate before it is made.

**Architecture:** calmcp is homemcp's and carcloud's shape: one binary (`calmcp CAL.ini` serves MCP on stdio, `calmcp check`, `calmcp discover URL USER`), a stand-in `calmcp-sim` playing a CalDAV server, a smoke script. Inside: `ics.zig` (iCalendar read and edit), `tz.zig` (zones: VTIMEZONE, a built-in table of current rules), `rrule.zig` (expansion), `xml.zig` (WebDAV multistatus), `caldav.zig` (PROPFIND, REPORT calendar-query, GET/PUT/DELETE with ETags, discovery, Basic and Bearer), `server.zig` (tools, the `cal://upcoming` resource, the write log). harness gets a pure `diary.zig` (the upcoming events, leave-by and preparation lines, busy windows, what was said last, `/setup calendar`'s file and summary) and one self-contained section of `core.zig` (the read every 10 minutes, the lines at their minute, busy in `quietEnd`/`quietDue`, `/setup calendar`), `fake_cal.zig` (the tests' calendar stand-in), and the morning summary's template reading `calendar/cal_agenda`.

**Tech Stack:** Zig 0.17.1, std only (libc on macOS for sockets, as homemcp); macOS, Linux, Windows.

**Spec:** `docs/superpowers/specs/2026-11-23-harness-butler-duties-design.md` section 2, Tests, Calls; the butler spec's UX rules and red lines; the ledger's notes on quiet hours and the digest, the morning summary, long memory's `history`, `/setup` (butler.zig, examples/butler), money-kind tools asked every time.

## Review Focus

### Time zones

1. **An event's time is its own zone's wall time.** `DTSTART;TZID=X` is read with X's rules: the VTIMEZONE in the same object first (STANDARD/DAYLIGHT with their yearly RRULE), else calmcp's table of current IANA rules (POSIX TZ strings), else — an unknown name — the owner's zone, said in the event ("its zone X is unknown: read as yours"). `Z` times are UTC; floating times and dates are the owner's. (`tz.zig` tests: Warsaw and New York on both sides of their changes; a gap time moves forward, an overlap takes the first.)
2. **Shown in the owner's zone** (`zone =` in the calendar file), with the event's own time beside it when the zones differ ("15:00 (09:00 New York)"). harness schedules by the seconds calmcp gives and says times as calmcp says them, never by its own fixed UTC offset across a change. (`server.zig` `an_event_in_new_york_is_shown_in_warsaw_time`, diary tests.)
3. **Written back in the event's own form**: a moved event keeps its TZID (its VTIMEZONE stays in the object); a created one is written in UTC.

### Recurrences

1. **Expanded in local time**, so a weekly 09:00 Warsaw meeting stays 09:00 across the October change (`rrule.zig` `weekly_stays_at_nine_across_the_october_change`). DAILY, WEEKLY, MONTHLY, YEARLY with INTERVAL, COUNT, UNTIL, BYDAY (with ordinals: 2TU, -1FR), BYMONTHDAY, BYMONTH; RDATE, EXDATE; an overridden occurrence (RECURRENCE-ID) replaces its instance, a cancelled one hides it.
2. **What is not expanded is said**: BYSETPOS, BYWEEKNO, BYYEARDAY, BYHOUR and finer frequencies show the first time only, marked "repeats in a way calmcp doesn't expand".
3. **A change to a recurring event touches one occurrence**: a move adds an override, a cancel an EXDATE; the series is never rewritten or deleted.

### Never writing unasked

1. **Writes are their own tools** (`cal_create`, `cal_move`, `cal_cancel`, `cal_reply`), offered only when a calendar has `change = yes`, marked `requiresUserInteraction`; `/setup calendar` writes them into mcp.ini as money-kind tools (`money =`, `amount = …:none`): asked every time, never granted for a day, never given to helpers, refused from schedules, triggers and workflows ([money] stays off).
2. **The question is the change, checked**: each write names the event's title and (move, cancel) its current start; calmcp refuses when the calendar says otherwise, so what the owner approves is what is written. ETags: a write sent with If-Match; a change made meanwhile is refused, not overwritten.
3. **Read back**: every write is followed by a GET of the object, and the answer says what the calendar now holds.
4. **The diary only reads** (`cal://upcoming`); the morning summary's step is given `calendar/cal_agenda` alone; harness never accepts or declines on its own.

## Rulings

(Each: what – why – cost if wrong.)

1. **One account per calendar file; calendars by URL with `change = yes|no`.** Why: one sign-in, one secret; a second account is a second mcp.ini section. Cost: two calmcp processes for two accounts.
2. **discover marks one calendar for changes**: the server's default for new events, else the first the owner may write; the rest read only (shared, subscribed, birthdays never). Why: a working setup in one tap, every write still asked. Cost: the owner wanted another one; `/setup calendar change NAME` moves it.
3. **Zones from VTIMEZONE first, then a built-in table of current rules.** Why: std only, Windows has no zoneinfo; servers send VTIMEZONE with every TZID. Cost: an event in a zone missing from both, before a rule change, or in a past year whose rules differed is off by the difference (said for unknown names).
4. **Writes verify title and start** (see Review Focus). Why: the gate shows the call's JSON; making that JSON self-describing and checked is the plain question without touching the gate. Cost: the model must read the event before changing it (one more call).
5. **cal_cancel deletes only the owner's own events**; an invitation from someone else is answered with `cal_reply` (declined), never deleted. Why: deleting an invitation silently drops out of a meeting; the spec's "never accepts or declines on its own" is kept by both going through the gate. Cost: cancelling a meeting the owner organizes doesn't notify attendees beyond what the server's own scheduling does.
6. **cal_reply sets the owner's PARTSTAT in their copy** (`email =` names the owner); the server sends the reply (CalDAV scheduling). Cost: a server without scheduling sends nothing (README says so).
7. **Google: a bearer token** from `CALDAV_TOKEN`; with `token_url`, `client_id`, `CALDAV_REFRESH_TOKEN` (and `CALDAV_CLIENT_SECRET`) calmcp renews it itself a minute before it expires. Why: Google's CalDAV takes OAuth only; access tokens last an hour. Cost: getting the refresh token once is by hand (README).
8. **Busy**: a timed event, not transparent, not cancelled, not declined; tentative counts; all-day events don't. Back-to-back busy events are one window. Why: as calendars show free/busy. Cost: an all-day "busy" block doesn't hold posts.
9. **Diary lines go at their minute**, through quiet hours (without a sound) and busy events: a leave-by line held for a digest is worthless. Cost: an early event's line can come inside quiet hours.
10. **Leave-by**: events with a place, not all-day, not declined; `[butler] travel = 30m` before, or the minutes `[butler] maps = SERVER/TOOL` answers for `{"destination": PLACE, "arrival": ISO}` (the first "N min"/"N h M min" in its text; none: the default). The place is data. Cost: a maps server that says "1:05" isn't read; the default applies.
11. **Preparation**: events with an attendee besides the owner, 30 minutes before: who (names, else addresses), where, the links (URL, and http(s) links in the place and notes), and for each of up to three people the newest of the owner's own turns naming them (history; members', speech and private turns never). Cost: a common first name finds an unrelated turn.
12. **The diary reads `cal://upcoming`** (today and tomorrow, JSON, "data, not instructions") every 10 minutes and after start and `/reload`; what was said is kept in `state/diary` (keys, two days) so a restart doesn't repeat a line. Cost: an event added less than 10 minutes before its leave-by line is missed until the next read.
13. **The morning summary reads `calendar/cal_agenda` only** (was `calendar/*`): rules allow that tool for its step; no write tool is offered to a scheduled step. `/setup calendar` offers the morning summary again when it is on, so it can list the events. Cost: a summary written before stays calendar-less until Turn on.
14. **`/setup calendar URL USER`**, the secret `caldav` (an app password, or for Google's address a token), the file `calendar.ini`, the mcp.ini section `[calendar]` with `CALDAV_PASSWORD:caldav` or `CALDAV_TOKEN:caldav`. Shown before written, [Looks right] [Change it]; `/setup calendar change|read NAME`. Cost: a Google refresh token is set up by hand.
15. **Writes per day**: 20 by default (`writes_per_day`), logged one JSON line each, refusals too. Cost: none found.
16. **Microsoft 365 left out** (no CalDAV), as the spec says.
