# harness: Undo (Part 2 of the 2026-11-23 spec) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A run that changed files in folders that keep snapshots ends its message (the chat reply, a task's or trigger's post; harness's line when it ended on a limit or an error) with "Changed N files in A/ and B/." and an **Undo** button (`u<run>-<16 hex of HMAC-SHA256(run number, the log's key)>`; the terminal prints `/undo RUN` instead). Undo takes back that run's changes file by file from its "before" and "after" snapshots: a file as the run left it gets its old content and mode back (removed if the run made it, made again if the run removed it); a file changed since is left and listed; a database's `-wal`, `-shm` and `-journal` files go with it and are left with it; each folder it writes in is snapshotted first (by the owner), so `/restore` takes the undo back. Refused while a run is going, and "too old to undo: its snapshots were pruned". `/undo` (the newest run with changes in this conversation), `/undo RUN`, `harness undo RUN`. Log kind `files`, event `undo` (run, folders, undone, left).

**Architecture:** `snapshots.zig` gets the run's pairs (a header names its conversation and, for a helper's "before", the run that delegated it: `parent`), `diff` between two snapshots, `undo` (pairs, groups of a file with its database side files, now-vs-after-vs-before per group, the snapshot first, deletes then writes, the log line) and `newestRun`. A new `undo.zig` holds the button's data and its HMAC check, the "Changed …" line and the outcome's words. `agent.zig` keeps the run's pair ids in `SnapRun`, takes the "after" snapshots once — at the run's final post, else at its end — and puts what changed on `Run.changed`, which `postThrough` hands to the outbox with a final post (`Post.changed`). `core.zig` appends the line and the button in `postShaped` (and to harness's own line when a chat turn, task or trigger run ended early), takes the press (`u…`) and `/undo [RUN]`; `telegram.zig` keeps the pressed message's text; `main.zig` prints `/undo RUN` in the terminal and adds `harness undo RUN`.

**Tech Stack:** Zig 0.17.1, std only; macOS, Linux, Windows.

**Spec:** `docs/superpowers/specs/2026-11-23-harness-routines-undo-copies-memory-design.md` Part 2, its tests and "Calls I made"; the overview's Snapshots (`2026-11-22-harness-platform-overview.md`); gap 3's store (`2026-11-22-harness-file-roles-design.md`, plan `2026-11-22-file-roles.md`, Ruling 5: helpers share their parent run's snapshots).

## Rulings

1. **The "after" snapshots are taken at the run's final post.** What: when a run posts its reply (a final `send`, or harness's post of its last text), the "after" snapshot of each folder it snapshotted "before" is taken just before the post, once; the run's end then only prunes. Why: the message must say what the run changed, and it goes out before the run ends; after a final post no call of the run runs (the turn ends), so it is the snapshot the end would take. Cost if wrong: a command that keeps writing in the background between the final post and the turn's end (milliseconds) is not in the "after" snapshot.
2. **A snapshot's header names its run's conversation, and a helper's names the run that delegated it (`parent`).** What: `{"…","by":…,"conversation":"main","parent":41,"when":…}` (each only when set). A run's pair is the "after" with `rid` = RUN and the "before" with `rid` = RUN (no parent) or `parent` = RUN. Why: Ruling 5 of gap 3 keeps the helper's rid on the "before" it takes, and `/undo` must find "the newest run with changes in this conversation" without a state file ("no state kept"). Cost if wrong: snapshots from before this change have neither: `/undo` without a number doesn't find those runs, and a run whose "before" a helper took then is "too old".
3. **Three states per file: as the run left it, as before the run, changed since.** What: a file (with its database's side files, as one group) is put back only when every one of them is now exactly as the run's "after" has it (content and executable bit, or absent); when every one is as the run's "before" has it, there is nothing to do (a second Undo says the run's changes are undone already); otherwise the group is left and listed. A link or a folder where a file was, or a link on the way, is "changed since". Why: never overwrite a later change, and a second press must not list every file as changed since. Cost if wrong: none found.
4. **Side files: `X-wal`, `X-shm`, `X-journal` belong to `X` when `X` is a file in the run's "before" or "after".** What: the group is `X` and those of its side files that either snapshot has or that exist now; a side file appearing since (a WAL made after the run) makes the group "changed since". A side file whose `X` is not a file is a file of its own. Why: a database in WAL mode often changes only its `-wal` (and `-shm`); putting back the main file without them, or them under newer writes, breaks it. Cost if wrong: a plain file `notes-journal` next to a file `notes` is undone or left with `notes` — harmless.
5. **Undo snapshots only the folders it writes in.** What: the "before undoing run N" snapshot (when `hand`, by owner) is taken for each folder where it will write or delete, after deciding what to write; nothing to put back: no snapshot. Why: "before it writes"; a second press, or one where everything changed since, leaves no clutter in `/snapshots`. Cost if wrong: none.
6. **The press edits the message with the text Telegram sends with the press.** What: `callback_query.message.text` is kept (`telegram.Callback.text`) and passed through `Core.handleCallbackText` (`handleCallbackIn` passes ""); the outcome is appended to that text (cut to fit 4,096 bytes, the outcome whole); where there is no text (an older message, a channel that can't edit) the button is cleared and the outcome is said in that conversation. Why: "edits the message with the outcome" with no state kept for it. Cost if wrong: one field and one line in main.zig.
7. **"A run is going" is `/restore`'s check** (the chat busy or a message queued, a background job — task, brief, trigger, workflow — going, a reload). A press then says so in its conversation and keeps its button. Why: the overview's restore rule; the owner can press again. Cost if wrong: none.
8. **Harness's line for a run that ended early carries it too.** What: a chat turn, task or trigger run that ends on a limit or an error after changing files: its line ("Step limit reached for this turn.", "[watch] Time limit reached…") ends with the "Changed" line and Undo. A stopped run, a task's NOTHING, a workflow's agent step and a refused reply post nothing: no button (`/undo RUN` works). Why: that line is the run's message then, and the moment Undo is wanted most. Cost if wrong: none.
9. **The run number is its id in the log (`rid`)**, as `/session` and `harness log session` use it. `/undo` with no number takes the highest run number of this conversation whose snapshots show changes (a run already undone counts, and says so); a helper's own number finds nothing (its changes are its run's). Why: one number everywhere. Cost if wrong: the owner gives the number.
10. **What a run that is not found says.** A press (its run certainly changed files): "Too old to undo: its snapshots were pruned." `/undo RUN` with no snapshot of RUN left: "Nothing kept for run N: too old to undo, or it changed no folder that keeps snapshots." A run with some folders pruned: those folders are named ("site/: too old to undo, its snapshots were pruned.") and the rest is undone. Why: the store can't tell a pruned run from one that never changed anything without reading the whole log. Cost if wrong: a wording.
11. **`harness undo RUN` opens the data folder as `harness snapshot restore` does** (refused while `harness run` or `harness chat` holds it: "already running"), with a role of its own (`undo`, no tools started). Why: the brief's rule. Cost if wrong: none.
