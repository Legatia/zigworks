## 1. Building blocks in Zig: bindings, river, other Zig compositors, pure-Zig Wayland, Zig 0.17 support

### Takeaway
Isaac Freund's stack (zig-wayland, zig-wlroots, zig-xkbcommon, zig-pixman) and river all build on Zig 0.17 as of early November 2026; river 0.5.2 (10 Nov 2026) requires exactly the reader's Zig 0.17.1 and wlroots 0.20. The small bindings followed Zig 0.16 and 0.17 within 3-5 days; zig-wlroots and river took 6-12 days for 0.16 and 35-40 days for 0.17. Pure-Zig, no-libwayland server-side code exists only as tiny hobby projects.

- Other Zig compositors found all sit on wlroots: byway, zwm, and teruwm (see section 10) — [byway](https://github.com/dreinharth/byway), [zwm](https://github.com/binarylinuxx/zwm), [teruwm write-up](https://teru-sh.pages.dev/blog/building-wayland-compositor-zig)

### Inferences
- (Inference from the dates above) Lag behind Zig releases: 0.16.0 (13 Apr 2026) -> zig-wayland +3 days, river v0.4.4 +6 days, zig-wlroots +12 days. 0.17.0 (1 Oct 2026) -> zig-wayland / zig-xkbcommon / zig-pixman +5 days; zig-wlroots +35 days (3 days after 0.17.1); river v0.5.2 +40 days (8 days after 0.17.1). River skipped 0.17.0 and went straight to 0.17.1. A project pinned to this stack should expect to be blocked for roughly one to six weeks after each Zig release, or carry its own patches.
- (Inference) Because the whole stack is maintained by essentially one person and tracks exactly one Zig version and one wlroots version at a time, a tool built on it inherits two moving pins (Zig minor, wlroots minor).
- (Inference) River itself is a candidate base rather than only a reference: an agent controller could be written as a river window-manager client (river-window-management-v1) plus a capture client, without forking the compositor. Whether river starts cleanly under `WLR_BACKENDS=headless` was not verified in this pass.
- (Inference) No pure-Zig server-side Wayland library is mature enough to depend on; a no-libwayland route means writing or vendoring the wire protocol and a scanner (the wire format itself is small; Payn/zig-wayland and shimizu are usable as reading material).

## 2. wlroots: headless backend, software rendering, version, API stability, static linking

### Takeaway
wlroots 0.20 (late March 2026) is current and is what river, zig-wlroots, sway 1.12 and labwc target; it has a headless backend and a pixman software renderer selected by environment variables. A static wlroots archive is packaged by Alpine, but I found no worked example of a fully static wlroots compositor built from build.zig; on musl every C dependency has to be built static too.

### Cited Findings
- wlroots 0.20 was reported released on 27 Mar 2026 together with sway 1.12-rc1; headline items were color-management-v1 and HDR10 on the Vulkan renderer, color-representation-v1, ext-workspace-v1, and foreign-toplevel support in ext-image-capture-source-v1 — [Phoronix](https://www.phoronix.com/news/wlroots-0.20-Sway-1.12-rc1), [Phoronix rc coverage](https://phoronix.com/news/wlroots-0.20-released)
- sway 1.12 was released 25 May 2026 on wlroots 0.20.0, with "support for capturing individual windows", wl_fixes, xdg-toplevel-tag-v1, ext-workspace-v1 — [Linuxiac](https://linuxiac.com/sway-1-12-wayland-compositor-released-with-hdr10-and-window-capture/), [sway 1.12 release notes mirror](https://newreleases.io/project/github/swaywm/sway/release/1.12)
- Environment variables (text from the old GitHub mirror of wlroots, which is stale but shows the long-standing names): `WLR_BACKENDS` "comma-separated list of backends to use (available backends: libinput, drm, wayland, x11, headless, noop)"; `WLR_RENDERER` "forces the creation of a specified renderer (available renderers: gles2, pixman)"; `WLR_HEADLESS_OUTPUTS` "when using the headless backend specifies the number of outputs"; `WLR_LIBINPUT_NO_DEVICES` "set to 1 to not fail without any input devices"; `WLR_RENDERER_ALLOW_SOFTWARE` "allows the gles2 renderer to use software rendering" — [wlroots docs/env_vars.md (swaywm mirror)](https://raw.githubusercontent.com/swaywm/wlroots/master/docs/env_vars.md)
- With the pixman renderer wlroots does not advertise linux-dmabuf (reported in a wayland-explorer issue; secondary source via search summary) — [wayland-explorer issue 81 mirror](https://github.imc.re/vially/wayland-explorer/issues/81)
- wlroots is commonly described (its own README tagline) as "about 60,000 lines of code you were going to write anyway"; an older README said about 50,000 — [wlroots README mirror](https://github.com/swaywm/wlroots)
- API churn evidence: zig-wlroots and river each needed a dedicated "update to wlroots 0.20" change (27 Mar and 31 Mar 2026); the teruwm author hand-wrote externs against `wlroots-0.18` — [zig-wlroots](https://codeberg.org/ifreund/zig-wlroots), [river releases](https://codeberg.org/river/river/releases), [teruwm write-up](https://teru-sh.pages.dev/blog/building-wayland-compositor-zig)
- Distribution lag: Ubuntu 26.04 (resolute) ships libwlroots-0.19-dev 0.19.2-1; no official 0.20 package was found for it; Ubuntu 24.04 (noble) carries the 0.17 series — [packages.ubuntu.com resolute](https://packages.ubuntu.com/resolute/libwlroots-0.19-dev), [Launchpad wlroots 0.17.2-2](https://code.launchpad.net/ubuntu/+source/wlroots/0.17.2-2)
- Static linking: Alpine publishes a `wlroots-static` package (listing showed 0.19.0-r0), i.e. a static libwlroots archive is a supported build output — [Alpine package](https://pkgs.alpinelinux.org/package/edge/community/x86/wlroots-static)
- On Ziggit, for a static musl executable "you are going to have to build static musl linked versions of e.g. libwayland.a and its dependencies"; users also report `.preferred_link_mode = .static` / `-search_static_only` not taking effect for system libraries — [ziggit: X11/Wayland with musl](https://ziggit.dev/t/how-to-build-x11-wayland-programs-when-linking-with-musl/6686), [ziggit: static linking help](https://ziggit.dev/t/need-help-with-static-linking-of-an-executable/9586)
- labwc's build automatically downloads and builds wlroots as a Meson subproject when the right system version is missing (`--force-fallback-for=wlroots`) — one existing pattern for vendoring an exact wlroots — [labwc README](https://github.com/labwc/labwc/)
- A related example of statically linking a hard C dependency from Zig exists: Mason Remaley, "Statically linking PipeWire" (31 Dec 2025); only the title/aggregator entry was seen — [scour.ing entry](https://scour.ing/p/https://gamesbymason.com/blog/2025/statically-linking-pipewire)

### Inferences
- (Background knowledge, not re-verified) Current wlroots also has a `vulkan` renderer value, and its Meson options allow disabling the DRM/libinput/X11 backends, the GLES/Vulkan renderers and Xwayland, which would shrink the dependency set for a headless-only build to roughly wayland-server, pixman, xkbcommon and libdrm headers. This is the configuration to test first if static linking is wanted.
- (Inference) "Single static binary" with wlroots is achievable in principle (static archive exists; headless + pixman needs no GPU stack) but means owning a build of wlroots, libwayland-server, libffi, pixman, xkbcommon (plus xkeyboard-config data files at runtime, which are not code and cannot be linked in without extra work) either via Meson outside Zig or by porting their builds to build.zig. No ready-made build.zig package for wlroots turned up.
- (Inference) GLES via llvmpipe is unnecessary for the stated tool: the pixman renderer composites shm buffers in software, and the only functional loss is no linux-dmabuf, which forces clients onto wl_shm (see section 3).
- (Inference) wlroots breaks API every minor release (roughly yearly: 0.19 in 2025, 0.20 in March 2026), so a wlroots-based tool must pin a minor version and cannot use the distro package on Ubuntu LTS anyway (26.04 has 0.19; the Zig bindings need 0.20).

### Gaps
- Official wlroots 0.20 release notes and current docs/env_vars.md could not be fetched (gitlab.freedesktop.org blocked). The exact 0.20.x patch level current in November 2026 is unknown (zig-wlroots is at 0.20.4-dev, which is the binding's own version).
- No confirmed example of a fully static wlroots-based compositor built with the Zig build system.

## 3. Not using wlroots: minimum protocol set per toolkit, Chromium/Electron without GPU

### Takeaway
A from-scratch shm-only compositor is feasible but the "minimal" set is larger than the six globals in the brief: Firefox aborts without wl_subcompositor, toolkits kill themselves on version mismatches, and popup positioning is where from-scratch compositors visibly break. Chromium has a first-class wl_shm path for software compositing and its own bots run against headless Weston, but I found no source that documents Chromium/Electron on a compositor with no dmabuf end to end.

### Cited Findings
- Chromium's Wayland buffer manager "creates wl_buffers based on dmabuf (hw accelerated compositing) or shared memory (software compositing)"; `CreateShmBasedBuffer` imports "a wl_buffer based on a shared memory file descriptor using wl_shm protocol"; `CreateDmabufBasedBuffer` uses zwp_linux_dmabuf; single-pixel buffers depend on the single-pixel-buffer protocol; the class has `SupportsDmabuf()`, `SupportsViewporter()`, `SupportsOverlays()` checks — [chromium: wayland_buffer_manager_host.h](https://raw.githubusercontent.com/chromium/chromium/main/ui/ozone/platform/wayland/host/wayland_buffer_manager_host.h)
- Chromium's Ozone docs say Wayland test suites need a Wayland server and that the build bots use Weston: `testing/xvfb.py --use-weston --no-xvfb ./views_unittests --ozone-platform=wayland`; xvfb.py runs Weston with the headless backend — [ozone_overview.md](https://chromium.googlesource.com/chromium/src/+show/main/docs/ozone_overview.md), [testing/xvfb.py](https://chromium.googlesource.com/chromium/src/+/282cd8a/testing/xvfb.py)
- Field reports: `--disable-gpu` "skips the part where electron figures that this won't work and moves straight to the software renderer"; some Electron apps "work ONLY with --disable-gpu"; other reports show blank or invisible windows and "GPU process exited unexpectedly" under native Wayland; "'--ozone-platform=wayland' is not compatible with Vulkan" appears in logs — [Arch forum](https://bbs.archlinux.org/viewtopic.php?id=305664), [NixOS discourse](https://discourse.nixos.org/t/electron-apps-work-only-with-disable-gpu/63851), [Obsidian forum](https://forum.obsidian.md/t/obsidian-doesnt-launch-in-wayland-mode-on-kde-multimonitor-setup/96386)
- Electron 38 changed the default of `--ozone-platform` to `auto` (Wayland when `XDG_SESSION_TYPE=wayland`, X11 otherwise) and deprecated `ELECTRON_OZONE_PLATFORM_HINT`; niri's docs say for Electron >= 39 use the command-line flag if an app does not default to Wayland — [Electron commit mirror](https://ayakael.net/mirrors/electron/commit/b9ceaabb857e0ec55c81b464facea77ebdddad44), [niri Application Issues](https://niri-wm.github.io/niri/Application-Issues.html)
- Firefox aborts with "We're missing subcompositor interface!" on a compositor socket without wl_subcompositor (gamescope) — [Mozilla bug 1867714](https://bugzilla.mozilla.org/show_bug.cgi?id=1867714)
- Version mismatches kill clients: Firefox died with "invalid version for global zwp_pointer_gestures_v1 (11): have 1, wanted 3", and would not start when it wanted wl_compositor v4 against a v3 compositor — [Mozilla bug 1919130](https://bugzilla.mozilla.org/show_bug.cgi?id=1919130), [Mozilla bug 1644312](https://bugzilla.mozilla.org/show_bug.cgi?id=1644312)
- Firefox deliberately crashes when a compositor rejects its wl_fixes global-removal ack; the global-removal race is a known protocol hazard — [Mozilla bug 2064274](https://bugzilla.mozilla.org/show_bug.cgi?id=2064274), [KDE blog 24 Mar 2026](https://planet.kde.org/vlad-zahorodnii-2026-03-24-addressing-global-removal-race-in-wayland/)
- A small independent compositor (hikari) had every GTK4 application crash, including gtk-demo — [hikari issue 26](https://hub.darcs.net/raichoo/hikari/issue/26)
- ewc, a Rust compositor with "No wlroots or smithay. No libwayland", after 125 commits lists partial wayland.xml (DnD, wl_output) and partial xdg-shell, plus linux-dmabuf v3 (GL only), viewporter, single-pixel-buffer, cursor-shape, layer-shell, fractional-scale; first goal is running foot, alacritty and mpv; "Qt popups don't work, though GTK does"; has a pixman software renderer (`EWC_NO_GL=1`) — [github.com/MaxVerevkin/ewc](https://github.com/MaxVerevkin/ewc)
- xwayland-satellite's stated minimum for a host compositor is a useful independent checklist: core interfaces (wl_output, wl_surface, wl_compositor, ...), xdg_shell (xdg_wm_base, xdg_surface, xdg_popup, xdg_toplevel) and wp_viewporter — [xwayland-satellite README](https://github.com/Supreeeme/xwayland-satellite)
- GTK 4 software path and switches: `GSK_RENDERER=cairo` "Selects the fallback Cairo renderer"; `GDK_DISABLE=gl` disables OpenGL; `GDK_DISABLE=dmabuf` disables dmabuf; `GDK_DISABLE=offload` disables subsurface graphics offload — [GTK 4 running docs](https://docs.gtk.org/gtk4/running.html)

### Inferences
- (Inference from the above plus background knowledge) Practical minimum global set for GTK 4, Qt 6, Firefox, Chromium/Electron, SDL and winit on shm: wl_compositor (v4+, ideally v6), wl_subcompositor, wl_shm, wl_seat (pointer + keyboard with an xkb keymap fd; v5+), wl_output (v2+ so `done`/scale work), wl_data_device_manager (v3), xdg_wm_base (toplevels and popups with correct positioner handling and grabs), and wp_viewporter. Strongly advisable next: xdg-decoration (to tell clients whether to draw their own title bars), wp_single_pixel_buffer, wp_presentation, primary-selection, text-input-v3, xdg-activation, cursor-shape, fractional-scale (can be omitted at scale 1). This list is my synthesis; only the wl_subcompositor (Firefox), xdg_shell + viewporter (satellite) and versioning hazards are directly documented above.
- (Inference) xdg_popup/positioner/grab semantics and wl_subsurface synchronised commit are the real cost in a from-scratch server, not the globals count: ewc's "Qt popups don't work" after 125 commits is the typical failure. Menus, combo boxes, tooltips and context menus are exactly what an agent has to click.
- (Inference) Advertise only what is implemented and at the versions implemented; toolkits degrade gracefully on a missing optional global much more reliably than on a present but incomplete one.
- (Inference) Chromium/Electron on an shm-only compositor should work via the software-compositing path (`--ozone-platform=wayland --disable-gpu`, or leaving the GPU process to fall back to SwiftShader and still presenting via wl_shm), since the code path is first-class and the bots exercise headless Weston; the field reports show the fragile part is the GPU-process fallback, so passing `--disable-gpu` explicitly is the safer default for an agent launcher. WebGL then depends on SwiftShader. Not verified by a source that names a no-dmabuf compositor.
- (Inference) Size: a compositor that implements the list above over raw sockets with a software blitter, an IPC and capture is on the order of 8-15k lines of Zig before it is robust across GTK 4, Qt 6, Firefox and Chromium. This is an estimate, not a measured figure (see section 10 for the few measured data points).

### Gaps
- No primary source enumerates the mandatory globals per toolkit (GTK 4, Qt 6, SDL 3, winit); this would have to be read from each toolkit's source or found by running them with `WAYLAND_DEBUG=1` against a stub.
- No documented test of Chromium or Electron against a compositor that advertises wl_shm but no linux-dmabuf (for example sway with `WLR_RENDERER=pixman`), and no list of known breakage for that case.
- Electron's official release notes for the 38 default change were not read directly (commit mirror only).

## 4. What the compositor position gives an agent, and what it does not

### Takeaway
Owning the compositor gives exact per-surface damage, commit timing, per-window buffers, window metadata, popups as separate objects, clipboard and prompt-free input, all without polling. It does not give semantics: the accessibility tree is a separate D-Bus system that must be started inside the private session, and several of the pixel-level benefits are now also available to an ordinary client of sway 1.12 or river through ext-image-copy-capture.

### Cited Findings
- ext-image-copy-capture-v1 already exposes compositor damage to clients: per-frame `damage` events ("regions that changed"; first frame is fully damaged, later frames report changes since the last `ready`), `presentation_time`, and after the first capture the compositor "may wait an indefinite amount of time for the source content to change" before copying. Sources can be outputs or toplevels (via ext-image-capture-source-v1). Only one frame object per session at a time. Option `paint_cursors` controls cursor compositing — [wayland.app: ext-image-copy-capture-v1](https://wayland.app/protocols/ext-image-copy-capture-v1)
- The protocol was merged into wayland-protocols staging in August 2024 as the successor to wlr-screencopy, which is now documented as deprecated — [Phoronix](https://phoronix.com/news/Wayland-Merges-Screen-Capture), [wlr-screencopy doc](https://isaacfreund.com/docs/wayland/wlr-screencopy-unstable-v1)
- Per-window capture exists in stock compositors in 2026: sway 1.12 (25 May 2026), river 0.4.2 (31 Mar 2026), wlroots 0.20 foreign-toplevel capture sources; KWin had an open request for these protocols — [Linuxiac on sway 1.12](https://linuxiac.com/sway-1-12-wayland-compositor-released-with-hdr10-and-window-capture/), [river releases](https://codeberg.org/river/river/releases), [KDE bug 513785](https://bugs.kde.org/show_bug.cgi?id=513785)
- A compositor can hold back and coordinate client updates: river waits for windows to commit buffers at requested sizes, with a short timeout, before presenting — [river blog post](https://isaacfreund.com/blog/river-window-management/)
- Typing text without key maps: zwp_input_method_v2 lets an input-method client `commit_string` at the cursor of the focused text input, receive `activate`/`deactivate` when a text field gains or loses focus, and receive `surrounding_text` (plain text around the cursor, with cursor and selection offsets) and `content_type` (purpose/hints) from the application; the application side is text-input-v3 — [wayland.app: input-method-unstable-v2](https://wayland.app/protocols/input-method-unstable-v2)
- Existing wrappers show the key-map problem that the input-method route avoids: kwin-mcp's `keyboard_type` is US-QWERTY evdev keycodes only; Unicode typing goes through `wtype` or a clipboard paste, and "some terminals receive Ctrl+V as a literal ^V" — [kwin-mcp on PyPI](https://pypi.org/project/kwin-mcp/)
- AT-SPI architecture: `at-spi-bus-launcher` claims `org.a11y.Bus` on the session bus and "launches the accessibility bus and manages its lifetime"; clients call `GetAddress` on `org.a11y.Bus` to find the separate accessibility bus; it launches on demand at `GetAddress` or immediately with `--launch-immediately`; `registryd` claims `org.a11y.atspi.Registry` on the accessibility bus and applications announce themselves to it; `org.a11y.Status` carries enabled / screen-reader properties — [at-spi2-core bus/README.md](https://gitlab.gnome.org/GNOME/at-spi2-core/-/raw/main/bus/README.md)
- The accessibility bus is separate because the interfaces are very chatty — [GNOME commits list, bus README change](https://mail.gnome.org/archives/commits-list/2021-November/msg10238.html)
- In a container without gnome-session "you'll have to launch the bus yourself": `/usr/lib/at-spi-bus-launcher --launch-immediately`, and it only worked when run inside the same `dbus-run-session` as the app — [GNOME Discourse](https://discourse.gnome.org/t/gsettings-set-org-gnome-desktop-interface-toolkit-accessibility-true-fails/15440)
- kwin-mcp relies on D-Bus activation of the distribution's `org.a11y.Bus` service inside its private `dbus-run-session`, with a direct-start fallback behind an environment variable; virtual sessions turn accessibility on — [kwin-mcp on PyPI](https://pypi.org/project/kwin-mcp/)
- GTK 4 selects its accessibility backend with `GTK_A11Y` (`atspi`, `accesskit`, `test`, `none`) — [GTK 4 running docs](https://docs.gtk.org/gtk4/running.html)
- Limits of AT-SPI in practice: "Chrome, Electron, and Qt expose little to AT-SPI" so OCR is the fallback; apps already running when accessibility was enabled need a restart (deskwright); "Some apps expose incomplete AT-SPI2 trees. Qt popup menus may be missing from the tree" (kwin-mcp) — [deskwright on PyPI](https://pypi.org/project/deskwright/), [kwin-mcp on PyPI](https://pypi.org/project/kwin-mcp/)
- waydriver drives GTK apps entirely through AT-SPI (XPath over the tree) inside headless Mutter with a private D-Bus — proof that the tree is reachable in a private session — [waydriver README](https://docs.rs/crate/waydriver/0.3.9/source/README.md)

### Inferences
- (Background knowledge of the core protocol, not re-fetched) The compositor sees, per surface: every `wl_surface.commit` with its `damage`/`damage_buffer` rectangles and attached buffer; every outstanding `wl_surface.frame` callback (a client that wants to draw again asks for one); xdg_toplevel `set_title` / `set_app_id` / parent / min-max size; xdg_popup creation with parent and anchor (menus and tooltips arrive as their own surfaces with known rectangles); subsurfaces; cursor surface/shape requests (a free "busy/ I-beam/ pointer" signal); `wl_data_source` offers and their MIME types (clipboard readable by the compositor at any time, no focus needed); text-input-v3 enable/disable (a free "a text field is focused" signal, plus cursor rectangle). It also decides who has keyboard/pointer focus and injects input simply by sending wl_pointer/wl_keyboard events, so no virtual-device protocol, portal or prompt is involved.
- (Inference) "Settled" at the compositor can be defined precisely as: no surface committed new damage for N milliseconds or K frame intervals, AND no client has an unanswered frame callback that it re-arms after each frame. This is strictly better than screenshot diffing: no pixel comparison, exact rectangles, and periodic small damage (caret blink, spinner) can be classified by rectangle and period instead of defeating the threshold (the blinking-cursor problem documented for openQA in section 9).
- (Inference) "Knowing when every client is idle" is only knowable as "no client is producing frames". A client that is waiting on the network or disk with no visual activity is indistinguishable from an idle one. This limit should be stated in the tool's documentation.
- (Inference) Deterministic stepping is the one capability no wrapper has: the compositor owns frame-callback delivery and the presentation clock, so it can freeze all clients (send no frame callbacks), deliver exactly one frame, and report which surfaces committed. It only controls rendering cadence, not client timers or network.
- (Inference) What an ordinary client of sway 1.12 / river already gets, narrowing the case for a custom compositor: output and per-toplevel capture with damage rectangles and change-driven wakeups (ext-image-copy-capture), toplevel lists with title/app_id (foreign-toplevel protocols), prompt-free input (virtual-keyboard / virtual-pointer protocols on wlroots), clipboard (data-control). What it does not get: which client committed and why, pending frame callbacks, popups as distinct objects with parent links (popups are composited into the toplevel capture), stepping, and a single process with one consistent event log.
- (Background knowledge, unverified here) Chromium only builds its accessibility tree when it detects assistive technology or is started with `--force-renderer-accessibility`; Qt needs `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1` or an enabled `org.a11y.Status`. An agent launcher would set these per app.
- (Inference) AT-SPI coordinates under Wayland are window-relative at best (clients do not know their global position), but the compositor knows every window's position, so the tool can map accessibility rectangles to screen pixels itself. This is a real advantage of owning the compositor that wrappers on KWin/Mutter need private APIs for.

### Gaps
- Whether toplevel capture in sway 1.12 / wlroots 0.20 returns full content for occluded or off-workspace windows was not confirmed by a source (kwin-mcp notes that with KWin's whole-workspace capture, "a window on an inactive desktop is absent from the image").
- No source read on wp_presentation, wl_data_device or text-input-v3 specifically; statements about them above are background knowledge.
- No documented recipe for a complete AT-SPI setup for Qt 6 and Chromium inside a private headless Wayland session.

## 5. X11 applications: Xwayland under a custom compositor

### Takeaway
Rootless Xwayland needs an X11 window manager plus the xwayland-shell association, which is a substantial separate program; in 2026 the cheap route is to spawn xwayland-satellite, which needs only xdg-shell and viewporter from the host. The X11-only tail is shrinking fast but is not gone.

### Cited Findings
- xwayland_shell_v1 lets the Xwayland server give a wl_surface the xwayland_surface role and associate it with an X11 window via a 64-bit serial (`set_serial`, matched to a `WL_SURFACE_SERIAL` client message); only Xwayland may bind the global and the compositor should hide it from other clients — [wayland.app: xwayland-shell-v1](https://wayland.app/protocols/xwayland-shell-v1)
- xwayland-satellite "grants rootless Xwayland integration to any Wayland compositor implementing xdg_wm_base and viewporter"; required from the host: core interfaces, xdg_shell, wp_viewporter; optional: linux-dmabuf, xdg-activation, xdg-decoration, xdg-foreign, pointer constraints, primary selection, tablet, fractional scale. Runtime dependencies: Xwayland 23.1+, xcb, xcb-util-cursor. Its README motivates the project by noting that rootless Xwayland support involves writing an X11 window manager. Known issues: some Java apps need `_JAVA_AWT_WM_NONREPARENTING=1`; MPL-2.0 — [xwayland-satellite README](https://github.com/Supreeeme/xwayland-satellite)
- niri integrates xwayland-satellite out of the box since 25.08 (needs satellite >= 0.7): it creates the X11 sockets, exports `DISPLAY`, and spawns satellite on demand when an X11 client connects — [niri Xwayland wiki](https://github.com/niri-wm/niri/wiki/Xwayland)
- With wlroots the Xwayland support is a library feature: dwl's Xwayland is "optional ... provided by wlroots" (needs libxcb, libxcb-wm, wlroots built with X11 support, Xwayland at runtime); river 0.5.1 fixed a race where Xwayland clients sometimes failed to open due to an upstream wlroots issue — [dwl README](https://codeberg.org/dwl/dwl), [river releases](https://codeberg.org/river/river/releases)
- Shrinking X11-only set in 2026: JetBrains IDEs enable native Wayland automatically from 2026.1 EAP (X11 can be forced with `-Dawt.toolkit.name=XToolkit`); Electron >= 38 defaults `--ozone-platform` to auto; KDE Plasma 6.7 is the last release with a native X11 session and GNOME has removed its X11 session; Godot's docs still say X11 remains the default for projects; GTK1/GTK2 applications require Xwayland — [JetBrains blog Feb 2026](https://blog.jetbrains.com/platform/2026/02/wayland-by-default-in-2026-1-eap/), [It's FOSS Oct 2026](https://itsfoss.com/projects-keeping-x11-alive/), [Godot docs](https://docs.godotengine.org/en/latest/tutorials/platform/linux/wayland_x11.html), [LWN comment thread](https://lwn.net/Articles/1026582)

### Inferences
- (Inference) For the stated tool, do not write an XWM. Either (a) use wlroots and its xwayland helper, or (b) ship without X11 and, when an X client is needed, spawn `xwayland-satellite` (which itself needs the `Xwayland` binary installed). Under (b) X11 windows arrive as ordinary xdg_toplevels, so capture, titles, damage and input all work unchanged; the cost is two extra external binaries, which breaks the "single binary" property only for X11 use.
- (Inference; background knowledge for the size) A native XWM (window mapping, override-redirect popups, ICCCM/EWMH properties, selections and drag-and-drop bridging, focus rules) is on the order of several thousand lines in wlroots and is the classic source of long-tail bugs; it is the least rewarding part to reimplement for an agent tool.
- (Inference) Agent-relevant software that still needs X11 in late 2026: Wine/Proton applications unless the Wine Wayland driver is selected, older Java/Swing and GTK2/Qt4-era tools, some proprietary engineering and EDA packages, games and Godot projects by default, and anything launched with X11 forced. Browsers, Electron apps, GTK 3/4, Qt 5/6, LibreOffice, JetBrains IDEs and terminals are native. This list is my judgement, not a sourced census.

### Gaps
- No sourced figure for how much desktop software is still X11-only in 2026; nothing found on Wine's Wayland driver default or Steam.
- xwayland-satellite's current version/date and whether it runs correctly against an shm-only (no-dmabuf) host were not confirmed.

## 6. Isolation and many instances

### Takeaway
One instance is one compositor process bound to a socket in its own XDG_RUNTIME_DIR, plus a private D-Bus session bus (and, if wanted, the accessibility bus); every existing agent wrapper does exactly this. Published per-instance memory numbers are almost nonexistent: about 200 MB for a headless GNOME Shell session is the only figure found.

### Cited Findings
- deskwright: each headless session has "its own session bus, its own `gnome-shell --headless`, and its own runtime directory" and "uses about 200 MB"; it caps sessions (default 4), takes a per-name start lock, and refuses to start below a free-memory floor — [deskwright on PyPI](https://pypi.org/project/deskwright/)
- kwin-mcp: each virtual session runs under `dbus-run-session` with a private session bus and `kwin_wayland --virtual`; isolation covers bus, display and input and is explicitly "not a filesystem or network sandbox" — apps run with the user's permissions and network access — [kwin-mcp on PyPI](https://pypi.org/project/kwin-mcp/)
- waydriver: each session gets its own compositor (headless Mutter), a private D-Bus, and its own app settings; the MCP image runs in Docker with `--network none`; screenshots/video come through PipeWire — [waydriver README](https://docs.rs/crate/waydriver/0.3.9/source/README.md)
- Minimal headless recipe from the PyGObject docs: `export XDG_RUNTIME_DIR=/tmp`, `eval $(dbus-launch --auto-syntax)`, `mutter --wayland --no-x11 --sm-disable --headless -- python my_script.py` — [PyGObject testing guide](https://pygobject.gnome.org/guide/testing.html)
- A WebKitGTK/bubblewrap failure shows sandbox interaction with the accessibility bus socket: "bwrap: Can't find source path /root/.cache/at-spi: Permission denied" — [Red Hat bug 2162351](https://bugzilla.redhat.com/show_bug.cgi?id=2162351)
- The only sway memory figure found is an anecdote of 216 MB at bare start on a FreeBSD desktop (not headless, not pixman) — [FreeBSD forums](https://forums.freebsd.org/threads/can-you-use-wayland-with-a-simple-window-manager.81606/latest)
- Weston's maintainers state that Weston and libweston "are not suitable for severely memory-constrained environments" — [Weston README mirror](https://gitee.com/mirrors_chromium_googlesource/weston)
- RSS overstates per-instance cost because shared memory is counted; PSS is the right metric — [Phusion: accurately measuring memory](https://www.phusionpassenger.com/library/indepth/accurately_measuring_memory_usage.html)

### Inferences
- (Inference) Instance layout for the tool: `XDG_RUNTIME_DIR=/run/user/UID/<tool>/<name>` (mode 0700) holding `wayland-0`, the D-Bus session socket and the AT-SPI socket; children get `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_TYPE=wayland`, and no `DISPLAY` (so nothing silently lands on a host X server). `XDG_SESSION_TYPE=wayland` matters for Electron >= 38's `auto` selection (section 3).
- (Inference) The compositor itself needs no privileges, no DRM device, no seat/logind and no input devices in headless mode, so it nests cleanly inside containers, user namespaces or bubblewrap. With a custom compositor the natural design is to spawn each app tree inside its own namespace/bwrap with only that instance's runtime dir bound in; the accessibility bus socket path has to be bound too (see the bwrap bug above).
- (Inference) Per-instance memory for a pixman headless compositor is dominated by buffers, not code: one 1920x1080 ARGB framebuffer is about 8 MB, and each client window's shm buffers (usually two or three per surface) are shared mappings counted against the client. A custom compositor should land in the low tens of MB of private memory; the applications (browser, Electron) are the real cost. This is an estimate; no measurement was found.
- (Inference) Per-instance services to decide on: a D-Bus session bus is effectively mandatory (GTK/Qt apps, portals, AT-SPI all assume it); xdg-desktop-portal is only needed for sandboxed (Flatpak/Snap) apps and for apps that insist on portal file choosers, and it needs a backend implementation — for an agent, forcing toolkit-native file dialogs (which are ordinary windows the agent can drive) is simpler than running portals; PipeWire is not needed for capture when the compositor does it itself (the Mutter/KWin wrappers need it or a private screenshot API), only for audio or WebRTC inside apps; fonts come from the host's fontconfig unless the app tree is put in a container, in which case a font set must be bound in.

### Gaps
- No published PSS/RSS numbers for sway, cage, labwc or Weston in headless + pixman mode, and none for "N instances per machine". These have to be measured.
- No source read on xdg-desktop-portal behaviour without a backend in a private session.

## 7. Existing compositors that already run headless: is a thin wrapper enough?

### Takeaway
Thin wrappers already exist and are shipping in 2026 on Mutter (waydriver, deskwright) and KWin (kwin-mcp); nobody found has done it on sway/wlroots or with a purpose-built compositor. Their published limitations (no per-window capture on KWin, polling-based waits, key-map-bound typing, ~200 MB sessions, heavy runtime dependency lists) are the concrete gaps a custom compositor would close.

### Cited Findings
- waydriver (Rust library + `waydriver-mcp`, 0.3.x in 2026): "Headless GUI testing for Wayland applications via AT-SPI accessibility APIs and PipeWire screen capture"; real Mutter with no monitor; input through Mutter RemoteDesktop; auto-wait for elements to be visible/enabled; backend traits (`CompositorRuntime`, `InputBackend`, `CaptureBackend`) with only GNOME/Mutter implemented — "KWin and Sway can be added as sibling crates" — [waydriver README](https://docs.rs/crate/waydriver/0.3.9/source/README.md)
- deskwright 0.1.1 (1 Sep 2026; 0.2.0b1 on 7 Oct 2026): MCP server + GNOME Shell extension; input via `org.gnome.Mutter.RemoteDesktop` D-Bus with absolute coordinates and keysyms; recording via Mutter ScreenCast with no consent dialog; tools include `wait_for`, `region_changed` (wait for pixels to change), `frames` (per-frame delta series), `zoom` (crop to a window/region/widget). Limits: only GNOME Shell 50 verified; KDE/Sway/Hyprland "input only"; needs logout/login after installing the extension — [deskwright on PyPI](https://pypi.org/project/deskwright/)
- kwin-mcp 0.12.0 (15 Oct 2026, 37 tools): input via KWin's private `org.kde.KWin.EIS.RemoteDesktop` D-Bus interface returning a libei fd, bypassing the portal dialog; screenshots via ScreenShot2 `CaptureWorkspace` with `spectacle` fallback; no single-window capture ("tracked as issue #34"; `CaptureWindow` unreachable because it needs an fd); waits are `wait_for_element` polling AT-SPI every 200 ms (5 s timeout) and `screenshot_after_ms`; no general idle/settle detection; three- and four-finger gestures are consumed by KWin; Qt popup menus may be missing from the tree — [kwin-mcp on PyPI](https://pypi.org/project/kwin-mcp/)
- hypruse targets a live Hyprland session (not headless), sending pointer events over the Wayland wire and typing via wtype — [hypruse on PyPI](https://pypi.org/project/hypruse/)
- Portal-based capture/input normally needs a human to approve each session; that is the obstacle the private Mutter/KWin D-Bus APIs sidestep — [pinggy blog](https://pinggy.io/blog/remote_desktop_into_wayland_without_a_vps/), [GNOME Discourse: persistent remote desktop](https://discourse.gnome.org/t/persistent-remote-desktop-access-api/19415)
- sway headless in practice: Vim's CI starts `WLR_BACKENDS=headless sway &` on GitHub Actions (since 21 Apr 2025) with `WAYLAND_DISPLAY=wayland-1` — [vim_dev commit](https://groups.google.com/g/vim_dev/c/nEOBnv9yQec/m/GZ_q9n7VBgAJ)
- sway 1.12 can capture individual windows; river 0.4.2+ likewise; a Rust crate (wlr-capture) captures windows via ext-image-copy-capture and uses Sway/Hyprland/niri IPC only to find the focused window, noting Wayland has no portable focus query — [Linuxiac](https://linuxiac.com/sway-1-12-wayland-compositor-released-with-hdr10-and-window-capture/), [wlr-capture docs](https://docs.rs/wlr-capture)
- wayvnc supports headless wlroots sessions (useful as a human debugging view) — [linuxlinks on wayvnc](https://www.linuxlinks.com/wayvnc-vnc-server-wlroots-based-wayland-compositors/)
- labwc "cannot be controlled with dbus, sway/i3/custom-IPC or other technology"; it only understands wayland-protocols and wlr-protocols — [labwc README](https://github.com/labwc/labwc/)
- Weston: test harness defaults to the headless backend with the noop renderer; `refresh` = 0 means "repaint only on demand" (for example when a screenshot is requested); breakpoints (`client_break` / `server_release` semaphores, `weston_test_breakpoint` from the weston-test protocol) pause and resume the server from a test — [Weston test-suite API](https://wayland.pages.freedesktop.org/weston/toc/test-suite-api.html)
- Firefox crashed on gamescope's Wayland socket because gamescope does not offer wl_subcompositor — gamescope's nested socket is not a general-purpose desktop — [Mozilla bug 1867714](https://bugzilla.mozilla.org/show_bug.cgi?id=1867714)

### Inferences
- (Inference) A wrapper on sway 1.12 headless is the strongest "no new compositor" option and appears to be unoccupied: `WLR_BACKENDS=headless WLR_RENDERER=pixman sway` + sway IPC (tree with titles/app_ids/rects, events) + ext-image-copy-capture client for output and per-toplevel capture with damage + virtual-keyboard/virtual-pointer clients for input + data-control for clipboard. In Zig all of those are plain Wayland clients written with zig-wayland (no wlroots linking), which sidesteps the static-linking problem but makes sway (and its wlroots) a runtime dependency, not a single binary.
- (Inference) What a wrapper on sway/river/Mutter/KWin cannot do, and owning the compositor can:
  1. Settle from causes rather than effects: per-client commit stream and pending frame callbacks, instead of "the composited output stopped being damaged".
  2. Deterministic stepping (freeze frame callbacks, advance one frame, controlled presentation clock). Weston's test breakpoints are the only stock analogue and are not a public control interface.
  3. Popups, menus, tooltips and subsurfaces as first-class objects with parent links and rectangles (capture protocols flatten them into the toplevel).
  4. Text entry through a built-in input method with field focus/`surrounding_text` readback, with no key map and no separate helper holding the input-method seat.
  5. Reading clipboard, cursor shape, title changes and focus changes as one ordered event log with a single clock ("what changed since last look" becomes a query against that log).
  6. Policy that suits an agent and nothing else: no animations, no decorations unless wanted, every window fully rendered regardless of stacking, never throttle hidden windows, fixed scale 1, fixed size, no idle/lock.
  7. One binary with no runtime dependency on a specific compositor version, and tens of MB instead of ~200 MB per session (the second number is the deskwright/GNOME figure; the first is my estimate).
- (Inference) What a wrapper keeps that a custom compositor has to earn: years of client-compatibility fixes (popups, DnD, Xwayland, IME edge cases) and free tracking of new protocols.
- (Inference) Mutter and KWin wrappers pull in a large runtime (gnome-shell or Plasma, PipeWire, Python/GObject stacks) and depend on private D-Bus interfaces; that is the opposite of the reader's single-binary CLI style.

### Gaps
- cage, niri, Hyprland headless outputs, Smithay's anvil and gamescope `--headless` were not individually verified for headless scripting in this pass; nothing citable was found on them.
- weston-test protocol request names (pointer move, key, button, screenshot) and reference-image fuzz comparison were not on the pages read (Weston source on gitlab.freedesktop.org was blocked).
- Mutter's exact headless flags beyond the PyGObject recipe (`--virtual-monitor`), and `kwin_wayland --virtual` documentation, were not found as primary docs; they are attested only through the wrappers that use them.

## 8. Testing in CI on GitHub ubuntu runners, and developing from macOS

### Takeaway
Headless Wayland compositors run fine on GPU-less GitHub runners (Vim does it with sway; Chromium and Weston do it with headless Weston). The friction is library versions: Ubuntu 26.04 only has wlroots 0.19 while the Zig bindings need 0.20. From macOS, a wlroots-linked build needs a Linux sysroot or VM, whereas a libc-free pure-Zig compositor would cross-compile directly.

### Cited Findings
- Vim's CI (commit 21 Apr 2025): installs `sway` via apt, runs `WLR_BACKENDS=headless sway &` then `disown`, sets `WAYLAND_DISPLAY: 'wayland-1'` in the workflow; a systemd user service did not work because GitHub Actions has no user session — [vim_dev commit](https://groups.google.com/g/vim_dev/c/nEOBnv9yQec/m/GZ_q9n7VBgAJ)
- A known pitfall on Actions: sway in the foreground hangs the step; started with nohup in the background, later clients failed with "Failed to connect to a Wayland server" (question used `WLR_BACKENDS=headless WLR_LIBINPUT_NO_DEVICES=1`; no confirmed fix shown) — [Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/70247332/use-headless-wayland-sway-when-testing-on-github-actions)
- Chromium's bots run Ozone/Wayland tests against a locally built Weston in headless mode with Xvfb disabled — [testing/xvfb.py](https://chromium.googlesource.com/chromium/src/+/282cd8a/testing/xvfb.py)
- Weston's own suite runs under `meson test` in GitLab CI; default harness setup is headless backend + noop renderer; DRM-backend tests use VKMS, a virtual KMS driver for headless machines — [Weston test suite](https://wayland.pages.freedesktop.org/weston/toc/test-suite.html), [Weston test-suite API](https://wayland.pages.freedesktop.org/weston/toc/test-suite-api.html)
- GTK's recommended backend for CI is `GTK_A11Y=test` ("recommended for test suites and remote continuous integration pipelines"); PyGObject's guide uses headless Mutter under `dbus-launch` — [GTK 4 running docs](https://docs.gtk.org/gtk4/running.html), [PyGObject testing guide](https://pygobject.gnome.org/guide/testing.html)
- waydriver runs its whole stack (headless Mutter, D-Bus, PipeWire, AT-SPI) inside a Docker image — [waydriver README](https://docs.rs/crate/waydriver/0.3.9/source/README.md)
- Ubuntu 26.04 ships wlroots 0.19.2; 24.04 has 0.17.x; river/zig-wlroots require 0.20 — [packages.ubuntu.com](https://packages.ubuntu.com/resolute/libwlroots-0.19-dev), [zig-wlroots](https://codeberg.org/ifreund/zig-wlroots)
- Static musl builds from Zig require static builds of libwayland and every other C dependency — [ziggit](https://ziggit.dev/t/how-to-build-x11-wayland-programs-when-linking-with-musl/6686)

### Inferences
- (Inference) CI plan for a wlroots-based build: run the job in a container image that has wlroots 0.20 (Alpine edge or Arch, to be checked at the time) or build wlroots 0.20 from source as a cached step; then `WLR_BACKENDS=headless WLR_RENDERER=pixman WLR_LIBINPUT_NO_DEVICES=1`. For a pure-Zig compositor: `zig build test` plus integration tests that start the binary and run real clients (`foot`, `gtk4-demo`, a Qt example, `chromium --ozone-platform=wayland --disable-gpu`) installed from apt, asserting on screenshots and the event log. No GPU, DRM, seat or systemd is needed either way.
- (Inference) The most valuable test asset is a protocol-conformance harness: scripted clients written against the tool's own wire library (or zig-wayland) that exercise xdg_popup positioning, subsurface sync, data-device and versioning, because toolkit failures (section 3) are otherwise only discovered by launching large apps.
- (Inference) macOS development options, in increasing fidelity: (1) cross-compile `-target x86_64-linux-musl` / `aarch64-linux-musl` on the Mac and run tests only in CI — works out of the box only if the binary has no C library dependencies, which favours the no-wlroots route for this particular developer; (2) a local Linux VM or container on Apple Silicon (Lima, OrbStack, UTM, Docker Desktop: aarch64 Linux) running the headless compositor and real clients — sufficient because nothing needs a GPU or a real display; view the result by having the tool write PNGs or by attaching a VNC/RDP bridge; (3) a remote Linux box or CI with an interactive debug session. A wlroots build on macOS itself is not possible (Linux-only APIs), so route (1) with wlroots would need a full Linux sysroot with headers and static libs.
- (Inference) aarch64 matters: Mac VMs are arm64, GitHub offers both x64 and arm64 Linux runners, so both should be in the test matrix from the start; Chromium/Electron under emulation is too slow to be a useful test.

### Gaps
- Whether an `ubuntu-26.04` GitHub-hosted runner image is generally available in November 2026 was not found.
- No source on running a headless Wayland compositor in Lima/OrbStack specifically; the macOS section is reasoning, not documented practice.

## 9. Prior art for deterministic UI stepping and settle detection

### Takeaway
Existing "settle" mechanisms are almost all pixel-similarity thresholds over repeated screenshots, with a well-documented blinking-cursor failure mode, or polling of the accessibility tree. Compositor-side mechanisms exist only in narrower forms: river's wait-for-commit-with-timeout, Weston's test breakpoints and on-demand repaint, and damage events in the capture protocol. No academic paper on settle detection for GUI agents was found.

### Cited Findings
- openQA `wait_still_screen(stilltime, similarity_level, timeout)`: default similarity 47 and timeout 30 s; "the default similarity for wait_still_screen is 47 which is tight enough that a flashing cursor usually fails it", so Fedora/Rocky tests loosen it to 42-45; one ticket notes it degenerating into "just a sleep 30" — [os-autoinst-distri-rocky commit](https://git.resf.org/testing/os-autoinst-distri-rocky/commit/670c2d4c9d1f9b164f8dfaf73de4a2617822e368), [openSUSE progress ticket 46679](https://progress.opensuse.org/issues/46679)
- Silk Test has `WaitForScreenshotStable` as a built-in synchronisation primitive — [Micro Focus Silk Test docs](https://www.microfocus.com/documentation/silk-test/210/en/silktestclassic-help-en/GUID-1A244B68-C7A0-40FD-A2D5-B48131AB7B12.html)
- TestDriver's redraw skill: compares consecutive frames, settled "when the diff between frames drops below 0.1% or the z-score is negative" over the last 10 measurements — [TestDriver redraw skill](https://cdn.jsdelivr.net/npm/@testdriverai/agent@7.9.3/ai/skills/testdriver-redraw/SKILL.md)
- Agent tool servers expose the same idea as a tool: Argent `await-screen-idle` (reports whether the screen went still before timeout), Android `wait_for_ui_stable`, `wait_for_settle`, `adb_wait_stable` — [Argent tool](https://glama.ai/mcp/servers/software-mansion/argent/tools/await-screen-idle), [mcp-android-emulator tool](https://glama.ai/mcp/servers/Anjos2/mcp-android-emulator/tools/wait_for_ui_stable)
- A 2026 practitioner write-up on GUI agents acting on stale screens recommends a masked pixel-similarity check around the click target, a global screenshot diff, and a window-system signal before each action — [tianpan.co, 18 May 2026](https://tianpan.co/blog/2026-05-18-gui-agent-right-button-wrong-screen)
- deskwright offers `region_changed` (wait for pixels to change), `frames` (per-frame delta series for judging motion) and `wait_for` (window, widget, text, focus or clipboard change); kwin-mcp polls AT-SPI (`wait_for_element`, 200 ms) and captures delayed frame bursts (`screenshot_after_ms`), and has no general idle detection — [deskwright](https://pypi.org/project/deskwright/), [kwin-mcp](https://pypi.org/project/kwin-mcp/)
- waydriver auto-waits for the target element to be visible and enabled before acting (Playwright-style actionability over AT-SPI) — [waydriver README](https://docs.rs/crate/waydriver/0.3.9/source/README.md)
- Compositor-side: river waits for clients to submit buffers for a configure before presenting, bounded by a short timeout — [river blog](https://isaacfreund.com/blog/river-window-management/)
- Compositor-side: Weston tests can set output refresh to 0 ("repaint only on demand") and use breakpoints with `client_break` / `server_release` semaphores to stop the compositor at defined points — [Weston test-suite API](https://wayland.pages.freedesktop.org/weston/toc/test-suite-api.html)
- Protocol-level: ext-image-copy-capture frames carry `damage` regions and a compositor may block a capture until the source changes — a standard "what changed since last look" primitive — [wayland.app](https://wayland.app/protocols/ext-image-copy-capture-v1)
- A 2026 preprint title in the area: "Why Are GUI Agents Correct but Late? Decode on the Decision-Time Critical Path, Tested with Pre-Compiled Policy Trees" (only the title was seen; it concerns agent latency, not settle detection as such) — [alphaxiv 2607.28399](https://www.alphaxiv.org/abs/2607.28399)

### Inferences
- (Inference) The gap in prior art is specific: nobody found exposes commit/damage/frame-callback state as an agent-facing "settled" signal. All agent tools infer it from pixels or the accessibility tree after the fact. A custom compositor's distinguishing feature would be `wait-settled` returning as soon as the clients stop committing, with the list of changed rectangles per window, and tolerant of periodic small damage by rule rather than by loosening a global threshold.
- (Background knowledge, not fetched: the DevTools page redirected) Headless Chrome has the closest thing to deterministic stepping in a browser: `HeadlessExperimental.beginFrame` with `--enable-begin-frame-control`, `--run-all-compositor-stages-before-draw` and `--deterministic-mode`, which lets the controller issue each frame and learn whether it had damage. It is a model for the API shape (step, hasDamage, optional screenshot) at desktop scope.
- (Background knowledge, unverified here) Android's instrumentation `waitForIdle` and Espresso idling resources, and Playwright's actionability checks, are the other established families: event-quiescence and element-state waits. A compositor gives the first family for free; the second needs AT-SPI.
- (Inference) A robust settle definition should combine: no damage for T ms; no unanswered frame callbacks; cursor shape not "wait/progress"; optionally AT-SPI "busy" state where available; and always a timeout with a report of which surfaces were still changing (the equivalent of Argent's "never settled" flag).

### Gaps
- No peer-reviewed or preprint paper specifically on screen-settle detection for GUI agents was found.
- dogtail, GNOME's Mutter test harness and Chromium's web-test timing controls were not read in this pass.
- openQA's actual similarity algorithm is only in the os-autoinst source, not in docs that were found.

## 10. Effort estimate signals

### Takeaway
With wlroots, a working compositor is hundreds to a few thousand lines and days of work (tinywl ~1,000 lines of C; a 3,700-line Zig compositor reported as built in a day); without wlroots, the only comparable from-scratch project found is still partial after 125 commits, and the library being replaced is about 60,000 lines. The agent-specific features are the small part; client compatibility is the large part.

### Cited Findings
- tinywl.c in an old wlroots snapshot (tag 0.4) is 928 lines / 35 KiB — [wlroots 0.4 tinywl mirror](https://git.nixnet.services/blankie/wlroots/src/tag/0.4/tinywl/tinywl.c)
- wlroots describes itself as about 60,000 lines "you were going to write anyway" (about 50,000 in an older README) — [wlroots README mirror](https://github.com/swaywm/wlroots)
- dwl's README says the original goal of 2000 SLOC is "impossible to maintain" for a reasonably complete compositor; dwl was at 0.9 / 0.10-dev in September 2026 — [dwl](https://codeberg.org/dwl/dwl)
- teruwm: a Zig tiling compositor on wlroots (hand-written externs for wlroots 0.18, no bindings generator), about 3,700 lines across 14 files, stripped binary under 1 MB, reported as built in one day by an author with a 37K-line Zig terminal already written; breakdown: ~400 lines wlroots bootstrap, ~300 lines terminal panes, ~3,000 lines everything else (input, cursors, bars, clipboard, screenshots, floating windows, Xwayland). Still "usable but not yet daily-drivable"; layer shell unfinished; keyboard-layout switching unreliable — [teruwm write-up](https://teru-sh.pages.dev/blog/building-wayland-compositor-zig)
- zig-wlroots ships a Zig port of tinywl as its example — [zig-wlroots](https://codeberg.org/ifreund/zig-wlroots)
- river: "over 6 years" of work by its author before the 0.4.0 architecture shipped; 36 releases — [river blog](https://isaacfreund.com/blog/river-window-management/), [river repo](https://codeberg.org/river/river)
- ewc (Rust, from scratch, no libwayland): 125 commits; xdg-shell and core protocol still "partial"; Qt popups do not work; full damage tracking and conformance are roadmap items — [ewc](https://github.com/MaxVerevkin/ewc)
- A university monograph argues that writing a Wayland compositor from scratch needs far more code than an X window manager and proposes a helper library for that reason — [USP monograph](https://linux.ime.usp.br/~mcmfb/mac0499/monograph.pdf)
- Way Cooler's post-mortem (Jan 2020) documents a compositor project that failed after library changes (wlc to wlroots) — [Way Cooler post-mortem](https://hn.jakechampion.name/reader/http://way-cooler.org/blog/2020/01/09/way-cooler-post-mortem.html)
- Wrapper-scale comparison: kwin-mcp reached 37 tools at version 0.12.0 by October 2026; deskwright reached 0.1.1 in September 2026 — both as wrappers around existing compositors — [kwin-mcp](https://pypi.org/project/kwin-mcp/), [deskwright](https://pypi.org/project/deskwright/)

### Inferences
All of the following are my estimates for one experienced Zig developer, not sourced figures.
- Route A, thin wrapper as Wayland clients of sway 1.12 or river headless (zig-wayland, no wlroots linking): roughly 2-4k lines; first useful version in 1-3 weeks. Delivers screenshot (desktop and per-window), damage-based "what changed", change-driven waits at output/toplevel granularity, input with no prompts, window list. Not a single binary; no stepping; settle is effect-based.
- Route B, own compositor on wlroots via zig-wlroots (start from the Zig tinywl): compositor core 1.5-3k lines, agent layer (IPC, capture/PNG, damage log, settle, input injection, input method, clipboard) another 3-5k; a few weeks to a first version, then ongoing work each wlroots and Zig release. Gets Xwayland, popups, DnD and client compatibility from wlroots. Single binary only with a self-managed static wlroots build; otherwise it ships with a libwlroots 0.20 dependency that Ubuntu LTS does not provide.
- Route C, pure-Zig compositor without libwayland or wlroots: 8-15k lines and several months before GTK 4, Qt 6, Firefox and Chromium are all dependable; the wire protocol, shm and blitting are a small fraction, xdg-shell popups/positioner/grabs, subsurfaces, data-device/DnD, seat focus rules, key-map handling (xkbcommon is the one C library that is hard to avoid: either link it or ship a fixed precompiled keymap and avoid layout logic by typing through the input method) and versioning are the bulk. In exchange: a true static single binary, trivial cross-compilation from macOS, no version pins other than Zig, and full control for stepping. X11 apps only via an external xwayland-satellite + Xwayland.
- The risk profile differs more than the line counts: A and B fail early and visibly (dependency/packaging), C fails late and per application (one toolkit's popup or IME path misbehaves months in). A staged plan that starts with A's client-side capture/settle logic and keeps the IPC stable would let B or C replace the backend later without changing the agent-facing commands.

### Gaps
- No current line counts for cage, sway, river, labwc, wayfire or the present-day tinywl were obtained (they would need a `cloc` run, which was out of scope for read-only web research).
- No from-scratch compositor write-up with a measured timeline to "runs GTK 4, Qt 6, Firefox and Chromium on shm" was found in any language; Smithay- and Go-based write-ups were not found in this pass.
- The teruwm "one day" claim comes from the author's own post (undated on the page) and describes a wlroots-based compositor by someone reusing a large existing codebase; it is not evidence for a from-scratch timeline.
