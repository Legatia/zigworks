# Build the headless desktop before the KVM

Build the headless desktop first, and build it in two stages: a thin Zig wrapper around headless sway 1.12 that fixes the command set and produces a published "screen settled" benchmark, then your own compositor behind the same commands. Both components already exist in some form as of November 2026, so neither is an empty field. On the desktop side every mainstream agent product still runs the old X11 stack with fixed two-second sleeps, and the half-dozen purpose-built agent compositors are weeks old, written in Rust, and mostly have 0 to 2 stars; nothing exists in Zig and nobody has published a settle-accuracy or memory-per-desktop measurement. On the hardware side the opposite holds: vendors ship agent integrations in firmware, some twenty community projects drive KVM devices for agents, and a Zig tool would add quality (one binary, real waiting, honest "no signal" states) but no new capability. The desktop is also the only one of the two that gives what you are after, which is control below the accessibility-and-synthetic-click layer: the display server sees every window's pixel updates at the moment they happen, and can freeze and step applications frame by frame, which no wrapper and no rival offers. The KVM tool is worth building second, as a small extension of headsight driving a roughly $15 serial-keyboard cable and capture dongle from your Mac, and it carries real abuse and security baggage that the desktop does not. Treat every number below with care: rival projects are tiny and untested by anyone but their authors, all performance figures are self-reported, the effort estimates are researcher inference, and nothing in this report was built or run.

## Every agent product still sleeps two seconds on X11

A few terms first. A **display server** is the program that owns the screen: applications hand it finished window images and it hands them input. On Linux there are two families. **X11** is the old one; **Xvfb** is an X11 server that draws into memory with no monitor, and **xdotool** fakes keyboard and mouse input for it. **Wayland** is the newer one, where the display server is called a **compositor**, and where an application cannot see or drive other windows unless the compositor allows it. That last property is why "prompt-free input" needs you to own the compositor, or at least be a trusted client of one.

Every mainstream product found runs the X11 stack and waits a fixed time after each action. Anthropic's reference demo uses Xvfb, the Mutter window manager, x11vnc and xdotool, and hard-codes `_screenshot_delay = 2.0` seconds ([computer.py](https://github.com/anthropics/claude-quickstarts/blob/main/computer-use-demo/computer_use_demo/tools/computer.py)). OpenAI's sample uses Xvfb, XFCE and xdotool with a fixed two-second wait ([OpenAI guide](https://developers.openai.com/api/docs/guides/tools-computer-use-integration)). E2B Desktop is built on the same stack ([template.py](https://github.com/e2b-dev/desktop/blob/main/template/template.py)), and so is Cua, the largest open project in the space at **32,609 stars**, whose Linux image is "XFCE on Xvfb" ([Cua Dockerfile](https://github.com/trycua/cua/blob/main/libs/images/linux/Dockerfile)). The OSWorld benchmark runs a full virtual machine with 4 GB of memory and `pause=2` ([desktop_env.py](https://github.com/xlang-ai/OSWorld/blob/main/desktop_env/desktop_env.py)). None of these owns its display server, and none runs Wayland by default.

The complaints follow directly from that design. In Cua's own measurements (on macOS) the screen changed 25 to 85 ms after an action while the tool returned after 1,103 to 1,900 ms ([cua#3971](https://github.com/trycua/cua/issues/3971)), and a click took about 1,040 ms with the polling step and about 14 ms without it ([cua#4055](https://github.com/trycua/cua/issues/4055)). On Linux, Cua's maintainers state that they have "no controlled fixture that records when the resulting surface update was actually presented by the compositor" ([cua#4012](https://github.com/trycua/cua/issues/4012)). That sentence is the gap in one line: the fact they cannot observe is a fact the compositor holds by definition. Users also report stale or black frames ([cua#5964](https://github.com/trycua/cua/issues/5964)), a cursor missing from captures ([e2b desktop#249](https://github.com/e2b-dev/desktop/issues/249)), and window-targeted input that does nothing in GTK 4 applications ([codex#50578](https://github.com/openai/codex/issues/50578)). The ground is also moving under the X11 stack: GNOME 50 is Wayland-only ([The Register](https://www.theregister.com/2026/03/19/gnome_50/)) and KDE Plasma 6.8 drops its X11 session ([It's FOSS](https://itsfoss.com/news/kde-plasma-to-drop-x11-support/)), both secondary reports. Speed is not the point for you, and it should not be the pitch either, because model thinking is 76 to 96 percent of task time ([OSWorld-Human](https://proceedings.mlsys.org/paper_files/paper/2026/file/5edb57c05c81d04beb716ef1d542fe9e-Paper-Conference.pdf)). The point is that a fixed sleep is a guess, and a guess produces both wasted seconds and screenshots taken before the screen finished changing.

### Ten small rivals appeared since September, none in Zig

The idea of a private desktop for the agent is no longer new. At least ten independent projects were created between September and November 2026, and they fall into two groups.

The first group builds a new compositor. All are in Rust, mostly on **Smithay** (a Rust library of compositor building blocks). **agentc** has 0 stars, was created on 11 November 2026, has about seven commits and a 3.7 MB binary; it offers a `wait_for_idle` that it says is "built on a 16x16 block hash diff, not on sleeps", and it admits that it has no GPU path, needs an outside helper for X11 applications, cannot open GTK 3 menus, and has no text-input support ([agentc](https://github.com/lin-calvin/agentc)). **fakeland** has 1 star, no licence, and was created the same day ([fakeland](https://github.com/zortax/fakeland)). **vway** has 1 star, dates from 20 October 2026, calls itself alpha, advertises "Honest synchronization", and gives each session its own private runtime directory, home directory and message bus ([vway](https://github.com/chpr8/vway)). waymux ([waymux](https://github.com/tek-cat/waymux)), mcpvil ([mcpvil](https://github.com/derekjchow/mcpvil)) and glasspane ([glasspane](https://github.com/oneilltomhq/glasspane)) are in the same range of 0 to 2 stars.

The second group wraps an existing compositor started without a monitor. **kwin-mcp** is the most adopted at 82 stars; it is Python, runs KDE's compositor with `kwin_wayland --virtual`, and says plainly that it is "not a filesystem or network sandbox" ([kwin-mcp](https://github.com/isac322/kwin-mcp)). **deskwright** runs a whole GNOME session per desktop at about 205 MB each and caps at four ([deskwright](https://github.com/tristanmuzzu/deskwright)). **linux-use** is the closest in spirit to your tools: a Go static binary of about 10 MB on headless labwc, with 8 stars ([linux-use](https://github.com/StivenKN/linux-use)). Several wrap sway and still fall back to fixed delays: one uses a fixed `settle_ms` of 150 ([wayhand-mcp](https://github.com/TimLai666/wayhand-mcp)), another a fixed 100 ms after shortcuts ([agent-desktop](https://github.com/jonatanferm/agent-desktop)). The largest related project, at 903 stars, drives the user's real desktop instead of a private one ([computer-use-linux](https://github.com/agent-sh/computer-use-linux)).

Adoption of the whole group is close to nil, and quality is unknown. No independent test of any of these projects was found, and none publishes how often its settle signal is right, how much memory one desktop costs, or how many desktops fit on a machine. A GitHub search for a Zig implementation returned nothing. The search did not cover GitLab, Codeberg, SourceHut or Reddit, so a small project hosted there could have been missed. What is missing across everything found is consistent: X11 applications handled inside the tool, a single static binary, published settle accuracy, measured memory and density, real isolation between desktops, and correct text entry for non-US layouts (kwin-mcp types US-QWERTY only, per its [PyPI page](https://pypi.org/project/kwin-mcp/)).

Demand is real but split. Evaluation teams hit cloud limits running fewer than 15 parallel OSWorld machines ([OSWorld#366](https://github.com/xlang-ai/OSWorld/issues/366)); a newer benchmark runs "native (no VM)" and resets a task in about one second with nested compositor instances ([hyprbench](https://github.com/crispwisp/hyprbench)); Codex users ask for a headless Linux server as a task environment ([codex#49491](https://github.com/openai/codex/issues/49491)). Hosted products want virtual machines and containers because they need file-system and network isolation, which a compositor does not give. Your audience is the other half: individual developers and test rigs that want an invisible second desktop on a machine they already trust. One caveat narrows the market further: Chromium's newer headless mode needs no display server at all, so web-only work does not need this tool.

## Owning the compositor buys seven things a wrapper cannot

It helps to be exact about what the compositor position gives, because part of it is already available without writing a compositor. An application tells the compositor which rectangles of its window changed (**damage**), then **commits** the new image, and asks to be told when to draw the next frame (a **frame callback**). A compositor therefore knows, per window and without comparing pixels, when something changed and whether the application intends to draw again. It also holds each window's image separately, its title and application identifier, menus and tooltips as separate objects (**popups**), the clipboard, and the cursor shape, and it can inject input with no permission prompt. It does not know what a button means; that still needs the accessibility tree or a vision model.

A good share of this now reaches ordinary client programs. The capture protocol `ext-image-copy-capture-v1` delivers damage and a presentation time with each frame ([wayland.app](https://wayland.app/protocols/ext-image-copy-capture-v1)), and sway 1.12, released on 25 May 2026, added capture of individual windows ([Linuxiac](https://linuxiac.com/sway-1-12-wayland-compositor-released-with-hdr10-and-window-capture/)). A wrapper can also type through the input-method protocol, whose `commit_string` call inserts text directly with no keyboard-layout table and whose `surrounding_text` lets the tool read the field back ([wayland.app](https://wayland.app/protocols/input-method-unstable-v2)). So a wrapper gets damage-based settling, per-window pixels and layout-independent typing.

What only an owned compositor gives is the researcher's list, and it is inference, not something a source demonstrates. First, settle from causes instead of effects: "no new damage for N milliseconds and no frame callback re-armed", with small periodic damage such as a blinking caret or a spinner classified by its rectangle and period. Second, **deterministic stepping**: hold back frame callbacks, let exactly one frame through, and look. No wrapper and no rival has this, and it is the clearest expression of "deeper control". Third, popups as first-class objects the agent can list. Fourth, a built-in input method. Fifth, one ordered log of every input and every window event, which is what an enforced, logged harness needs underneath it. Sixth, agent-only policy: no animations, every window fully drawn even when covered, scale fixed at 1. Seventh, one binary and tens of megabytes per desktop. Two limits apply to all of it. An application waiting on the network or the disk looks exactly like an idle one, so "settled" will never mean "done". And prior art warns that naive stillness detection decays: openQA's `wait_still_screen` is defeated by a blinking cursor ([Rocky commit](https://git.resf.org/testing/os-autoinst-distri-rocky/commit/670c2d4c9d1f9b164f8dfaf73de4a2617822e368)) and degenerated in practice into "just a sleep 30" ([openSUSE ticket](https://progress.opensuse.org/issues/46679)). No paper or project was found that exposes commit, damage and frame-callback state as an agent-facing settled signal.

### Three routes, from three weeks to several months

**wlroots** is the C library most small compositors are built on; it describes itself as "about 60,000 lines of code you were going to write anyway" ([wlroots](https://github.com/swaywm/wlroots)). It can run with no monitor and no graphics card through environment variables (`WLR_BACKENDS=headless`, `WLR_RENDERER=pixman`, where pixman is a software drawing library) ([wlroots env_vars](https://raw.githubusercontent.com/swaywm/wlroots/master/docs/env_vars.md)). **zig-wlroots** is the Zig binding to it; it requires Zig 0.17 and wlroots 0.20 and ships a small example compositor ([zig-wlroots](https://codeberg.org/ifreund/zig-wlroots)). The one serious Zig compositor, river, sits on this stack: version 0.5.2 of 10 November 2026 requires Zig 0.17.1 and wlroots 0.20, and represents more than six years of work ([river](https://codeberg.org/river/river), [river blog](https://isaacfreund.com/blog/river-window-management/)).

| | Route A: wrapper | Route B: own compositor on wlroots | Route C: pure Zig, no wlroots |
|---|---|---|---|
| What it is | Zig programs that are clients of headless sway 1.12 (or river) | A compositor written with zig-wlroots | A compositor that speaks the Wayland wire protocol itself |
| Size (researcher inference) | 2,000 to 4,000 lines | 1,500 to 3,000 lines of core plus 3,000 to 5,000 of agent layer | 8,000 to 15,000 lines |
| Time (researcher inference) | 1 to 3 weeks | a few weeks, then work at every wlroots and Zig release | several months |
| Single static binary | No: needs sway installed | Only with your own static build of wlroots and its C dependencies | Yes |
| Version pins | Zig, plus whatever sway the user has | Zig and wlroots 0.20 together | Zig only |
| Build on your Mac | Cross-compiles; runs only on Linux | wlroots does not build on macOS | Cross-compiles cleanly to Linux |
| Stepping and cause-based settle | No | Yes | Yes |
| X11 applications | Through sway's built-in support | Through wlroots' built-in support | Through an external helper only |
| Where it fails | Early and visibly: packaging | Early and visibly: dependencies | Late, one application at a time |

Route A is cheap and proven in the small: Vim's test suite already runs `WLR_BACKENDS=headless sway` on GitHub Actions ([vim_dev](https://groups.google.com/g/vim_dev/c/nEOBnv9yQec/m/GZ_q9n7VBgAJ)), and existing wrappers document the traps, such as creating a new virtual pointer for each action, which makes applications drop the first click ([headless-computer-mcp](https://github.com/UMCEKO/headless-computer-mcp)). It is also not the product: it is not one binary, it cannot step, and its settle signal is still observed from outside.

Route B is the fast way to own the compositor, and the size evidence is encouraging but thin. The wlroots example compositor is 928 lines ([tinywl](https://git.nixnet.services/blankie/wlroots/src/tag/0.4/tinywl/tinywl.c)), and one author reports writing a 3,700-line Zig compositor on wlroots in a day ([teruwm write-up](https://teru-sh.pages.dev/blog/building-wayland-compositor-zig)), an author claim. Its costs are structural. Ubuntu 26.04 packages wlroots 0.19.2, not the 0.20 the binding needs ([Ubuntu packages](https://packages.ubuntu.com/resolute/libwlroots-0.19-dev)), so neither your users nor the GitHub ubuntu runners have the library. A static build needs static builds of every C dependency ([Ziggit](https://ziggit.dev/t/how-to-build-x11-wayland-programs-when-linking-with-musl/6686)), and no worked example of a fully static wlroots compositor built from `build.zig` was found. And it breaks your habit of building on the Mac.

Route C fits your other tools best and costs the most. A compositor that implements the protocol itself has no C dependencies, links statically, and cross-compiles from macOS like trigrep does. The risk is compatibility with real applications, which shows up late. Firefox aborts if one optional-looking interface is missing ([Mozilla bug 1867714](https://bugzilla.mozilla.org/show_bug.cgi?id=1867714)). A comparable from-scratch Rust compositor reports after 125 commits that "Qt popups don't work, though GTK does" ([ewc](https://github.com/MaxVerevkin/ewc)). The hard parts are popup positioning, input grabs and nested surfaces, not drawing. Two facts make the route viable for an agent tool that needs no graphics card. Chromium has a first-class path for plain shared-memory images (`wl_shm`, as opposed to GPU buffers) ([Chromium source](https://raw.githubusercontent.com/chromium/chromium/main/ui/ozone/platform/wayland/host/wayland_buffer_manager_host.h)) and its own test machines run against a headless compositor ([Chromium docs](https://chromium.googlesource.com/chromium/src/+show/main/docs/ozone_overview.md)); GTK 4 can be told to draw in software with `GSK_RENDERER=cairo` ([GTK docs](https://docs.gtk.org/gtk4/running.html)). No source, however, documents Chromium or Electron running end to end on a compositor with no GPU buffer support, so this must be tested before committing. Existing pure-Zig Wayland server code is hobby-grade, for example a 0-star library targeting Zig 0.16 ([Payn/zig-wayland](https://codeberg.org/Payn/zig-wayland)).

The position this report takes: start with Route A, but write it so that the agent-facing commands and the event log do not mention sway, then replace the back end with **Route C**, not B. Route B's advantage is a head start of some weeks, and it is paid for with two version pins, a library your target distributions do not ship, an unproven static link and the loss of local builds. Route C's disadvantage is time, and time is the one cost you have said you accept. The decision between B and C should still be made on evidence from two short experiments described below, not on this reasoning alone.

### Develop on the Mac, prove on GitHub runners

Headless compositors run on machines with no graphics card: Vim's tests use sway on GitHub's runners, and Chromium's test machines use Weston. One documented trap: sway started in the foreground hangs the job step, so it must be backgrounded. For Route A and B the Ubuntu runner's old wlroots means running the job inside an Alpine or Arch container, or building wlroots 0.20 once and caching it. For Route C the Mac cross-compiles a static Linux binary and the runner only executes it. For day-to-day work a local Linux virtual machine on the Mac (Lima, OrbStack or UTM) is the practical answer for all three routes, and it needs no GPU; this is the researcher's suggestion, not a documented recipe. Test on both x64 and arm64 runners, because emulating Chromium is too slow to be useful. The most valuable test asset is a set of real applications driven through scripted steps with known correct end states, since that is what catches the late, per-application failures of Route C.

### First version, cheapest proof, and what can go wrong

The first version should do one thing well: start a private desktop, launch an application in it, send keys, clicks and text, capture one window or the whole desktop, and wait for settle, with every result reported as structured output and every event written to one log. Each desktop is one process with its own runtime directory and its own message bus, started with no privileges. Leave out GPU rendering, remote viewing, animations, multiple monitors, screen scaling, a built-in X11 window manager, and any claim of sandboxing. Leave out the accessibility tree at first, and say so, because it is a real hole: on Linux the tree (**AT-SPI**) runs over a separate message bus that must be started inside the same session as the application ([at-spi2-core](https://gitlab.gnome.org/GNOME/at-spi2-core/-/raw/main/bus/README.md)), and even then "Chrome, Electron, and Qt expose little to AT-SPI" ([deskwright](https://pypi.org/project/deskwright/)). The compositor's natural contribution later is converting the tree's window-relative rectangles into exact screen positions.

The cheapest test that shows the component is better: a fixed set of about twenty scripted actions across a GTK 4 application, a Qt 6 application, Firefox, and Chromium, run on GitHub runners against four setups (Xvfb with a two-second sleep, agentc, vway, and yours). Record for each action whether the capture taken at "settled" matches the true final screen, how long the wait took, and memory per desktop measured as PSS, the measure that splits shared memory fairly between processes, not the usual resident size that double-counts it ([Phusion](https://www.phusionpassenger.com/library/indepth/accurately_measuring_memory_usage.html)). Nobody has published this table. Route A is enough to produce its first version, and an earlier small measurement in another project suggests the effect is large: a fixed 0.2-second sleep dropped a keystroke in four of five runs where a settle wait passed five of five ([quern PR 101](https://github.com/quern-dev/quern/pull/101)).

The risks are mostly about dependencies. The whole Zig Wayland stack is essentially one maintainer, and it trails Zig releases: after 0.17.0 on 1 October 2026 ([Zig downloads](https://ziglang.org/download/index.json)) zig-wlroots took 35 days and river 40 to follow, by the release dates on their pages, so Route B stalls for up to six weeks at each Zig release; the smaller binding Route A needs followed within about a week. wlroots changes its interface at each yearly release (researcher inference). Route C removes those pins but keeps one hard C dependency candidate, the keyboard-layout library xkbcommon, which can be avoided by shipping one fixed layout and typing through the input method. X11-only applications are a shrinking but real tail: JetBrains tools default to Wayland from 2026.1 ([JetBrains](https://blog.jetbrains.com/platform/2026/02/wayland-by-default-in-2026-1-eap/)), while Wine, old Java and old toolkits still need X11. Do not write an X11 window manager; **xwayland-satellite** is a separate helper that provides X11 support to any compositor offering a short list of basic interfaces ([xwayland-satellite](https://github.com/Supreeeme/xwayland-satellite)), at the price of a second and third executable beside your single binary. One wrapper author reports intermittent X11 window failures in two recent wlroots versions ([agent-desktop](https://github.com/FilipNowakowicz/agent-desktop)), so the built-in route is not trouble-free either.

## Hardware control already ships in firmware, with no waiting built in

Terms again. A **KVM** device (keyboard, video, mouse) plugs into a computer's USB port and pretends to be a keyboard and mouse (**HID**, the USB class for input devices), and plugs into its HDMI port and pretends to be a monitor. An **IP-KVM** puts that behind a network address. The target needs no software, so the method works in the BIOS, in an installer, on a locked-down or broken machine, and on anything with a video output.

This component exists at every level, including vendor products. Sipeed's NanoKVM-Go, a crowdfunded device at an $89 list price that raised more than $130,000, ships an agent tool server in its firmware and is sold as the "world's first AI-native KVM", the vendor's phrase ([It's FOSS](https://itsfoss.com/news/sipeeds-nanokvm-go-crowdfunding/), [Sipeed wiki](https://en.wiki.sipeed.com/hardware/en/kvm/NanoKVM_Go/mcp.html)). TinyPilot publishes an official agent server ([tinypilot-mcp](https://github.com/tiny-pilot/tinypilot-mcp)) and put its automation interface behind a licence from $149 per year ([TinyPilot](https://tinypilotkvm.com/pages/automation)). PiKVM, the reference open project, has a free documented HTTP interface for sending keys and mouse moves, fetching a still image (with text recognition built in), switching power and mounting disk images ([PiKVM API](https://docs.pikvm.org/api/)). Device prices run from $24.99 for the DezKVM-Go to $399 for TinyPilot's Voyager 3, with JetKVM at $103 and PiKVM V4 at $275 to $385 ([Geerling](https://www.jeffgeerling.com/blog/2026/i-tested-every-ip-kvm/), [computingforgeeks](https://computingforgeeks.com/best-ip-kvm-homelab/)).

Around the devices sit some twenty community agent projects, all small. The most developed are a Python server for JetKVM with 25 stars and 25 tools ([jetkvm-mcp](https://github.com/shvartzj1/jetkvm-mcp)) and **kvm-pilot** with 19 stars, which has a `wait_for_state` call, mouse calibration and signed receipts, but admits that three of its seven drivers have never run on hardware ([kvm-pilot](https://github.com/DustinTrap/kvm-pilot)). The do-it-yourself end is just as populated: **serial-hid-kvm** (20 stars) drives a target from a roughly $15 pair of parts, with no authentication and ASCII-only typing ([serial-hid-kvm](https://github.com/sunasaji/serial-hid-kvm)); **kvmuse** does the same from macOS and is unusually frank that an acknowledgement from the keyboard chip "proves chip acceptance, not visible input on the target" ([spullara/openterface](https://github.com/spullara/openterface)); **vcctrl** uses a Raspberry Pi 5 and was shown driving a 1980s Macintosh ([vcctrl](https://github.com/ecliptik/vcctrl)). In Zig there is one abandoned project of 9 commits ([USBKVM](https://github.com/Kytezign/USBKVM)).

So existence is settled and adoption is thin. The official TinyPilot agent server has 0 stars months after launch. No benchmark of an agent working through a KVM has been published; the well-known benchmarks all run in virtual machines ([arXiv 2507.19132](https://arxiv.org/html/2507.19132v1)). The only latency figures are a competing vendor's 53 to 61 ms screen-to-screen for current devices ([WarpKVM](https://warpkvm.com/blog/ip-kvm-latency-benchmarks)) and one older independent reading of about 80 ms for JetKVM ([Geerling](https://jeffgeerling.com/node/3413)), and neither matters to an agent that thinks for seconds. What is missing, by the researcher's reading, is the same thing missing on the desktop side: waiting. Only one project has any wait call. None returns just the changed region. Few distinguish "no signal" from "black frame" from "frame unchanged" from "frame is old", and that distinction is the hardware version of a false success report. None is a single static binary.

### The first backend is a $15 cable pair on the Mac

Be clear about the ceiling: a Zig tool here adds quality, not a new capability class. Through a KVM the agent has only pixels, with no accessibility tree, no clipboard and no window list, so this is a tool of last resort for BIOS screens, boot menus, operating-system installs and machines where nothing can be installed. That also makes it the purest form of the control you want, since it works below the operating system itself.

The first backend should be the host-attached pair: a **CH9329** cable, which is a chip that turns serial-port bytes from your computer into a real USB keyboard and mouse on the target, and a **UVC** capture dongle, which makes the target's HDMI output appear as a webcam. The parts cost about $15, or $24.99 as a single product; the bare chip is $1.09 ([LCSC](https://www.lcsc.com/product-detail/C2838834.html)). The reason to start here is fit: your Mac sees a serial port and a camera, headsight already watches cameras and recognises text on-device, so the new code is a CH9329 driver of a few hundred lines (researcher inference; none exists in Zig) plus glue. The chip's absolute pointer mode addresses the screen on a 4095 by 4095 grid ([kvm-serial](https://sjmf.github.io/kvm-serial/SUPPORTED_DEVICES/)), which avoids mouse-acceleration guesswork wherever the target supports it. Dongle choice matters: the common MS2109 chip delivers 1080p only as compressed MJPEG at 30 frames per second and raw frames at 5 ([Delock datasheet](https://manualmachine.com/delock/88307/24864211-datasheet)), while the MS2130 delivers raw 1080p at 60 over USB 3 ([CNX Software](https://www.cnx-software.com/2022/10/09/10-hdmi-to-usb-3-2-video-acquisition-board-ms2130/)) and spares you a JPEG decoder.

The second backend is the PiKVM HTTP interface, which is plain web requests and JPEG stills and also covers GL.iNet's devices, whose firmware is a PiKVM fork. It adds power control and disk-image mounting, which the cable pair cannot do. The third is a Linux board in **gadget mode**, where the board itself acts as the USB keyboard and a key press is a plain write of 8 bytes to a device file. Leave out JetKVM, which has no still-image endpoint and requires a WebRTC connection and H.264 video decoding and warns that its interface is "subject to change"; leave out custom firmware on microcontrollers, even though MicroZig has a working USB keyboard example for the RP2040 family ([MicroZig](https://github.com/ZigEmbeddedGroup/microzig)); and leave out designing hardware, which saves no money against a $25 product.

The first version contains: type text, press keys, move and click with the absolute pointer, capture a frame, wait for a region to change, wait for settle, wait for text, and four honest observation states. It leaves out power control, virtual media, relative-mouse calibration, non-US layouts beyond one tested table, and any network listener. Effort is the smallest in this report, on the order of two to four weeks on top of headsight, and that figure is this report's inference with no source behind it. Development needs no Linux machine at all: the Mac is the host, and a spare computer, a Raspberry Pi or a cheap mini PC is the target.

The cheapest test: ten tasks on one target that no software agent can do, such as entering the firmware setup, changing the boot order, and walking an installer to its first reboot, run against kvmuse and serial-hid-kvm on the same $15 rig. Measure time from action to first changed frame, time to settled, characters typed per second with zero drops, and how often each tool reports success while the screen shows otherwise. That table would be the first of its kind.

### The FBI named these devices in October

The risks here are different in kind. On 13 October 2026 an FBI public notice stated that North Korean remote IT workers "use external hardware such as TinyPilot, PiKVM, GL.iNet, and other Keyboard Video Mouse (KVM) over IP devices" ([FBI IC3](https://www.ic3.gov/PSA/2026/PSA261013)), and Mandiant advises companies to restrict IP-KVMs ([Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/mitigating-dprk-it-worker-threat)). The devices themselves are a weak point: Eclypsium reported nine vulnerabilities across GL.iNet, NanoKVM, JetKVM and others and counted internet-exposed units rising from 404 to 1,611 ([Eclypsium](https://eclypsium.com/?p=16134)). A tool that lets a language model drive such a device will be read in that light. The defensible position is a tool for machines the operator owns: the device keeps its truthful USB and monitor identity, there are no concealment features, input stays disarmed until a person arms it, a read-only mode exists, every action goes to an append-only log, and the tool listens on nothing but the local machine. Defenders already detect these devices by USB name and by the monitor identity data (**EDID**) they present ([SANS ISC](https://isc.sans.edu/diary/Detecting+IP+KVMs/32824/)); a tool that tried to defeat that would deserve the suspicion.

The practical risks are friction. Apple-silicon laptops ask the user to approve a new USB accessory, and the Mac must be unlocked to do it ([Apple Support](https://support.apple.com/102282)), so a Mac as target is never fully hands-off on first contact; an unknown keyboard also triggers the keyboard identification assistant ([Apple Developer Forums](https://developer.apple.com/forums/thread/687750)). On your own Mac as host, camera access needs a permission grant. Elsewhere, firmware screens often ignore absolute-pointer devices, typing is slow and depends on the target's layout, a sleeping target and an unplugged cable both show black, captures can omit the cursor, and some laptops show their firmware screen only on the built-in panel. PiKVM's own documentation calls the USB-dongle path "high latency and low video quality" ([PiKVM FAQ](https://docs.pikvm.org/faq/)), which is acceptable for an agent and unpleasant for a human.

## Desktop first, as a wrapper that becomes a compositor

Build the desktop first. Three reasons carry the decision. The gap is larger: on the desktop side the mainstream is still fixed sleeps on X11 and the rivals are weeks old, while on the hardware side vendors already ship the feature. The fit with your motive is better: owning the display server is exactly the step below the accessibility-and-click layer, and stepping applications frame by frame is a capability nobody else has. And the harness you plan needs it: an enforced, logged harness is only as trustworthy as the event stream under it, and a compositor you own produces one ordered record of every input and every window change.

The form is staged, in this order. Stage one, about three weeks by the researcher's estimate: the wrapper on headless sway 1.12, with the final command names and the final log format, plus the settle benchmark against Xvfb, agentc and vway, published. Stage two, two experiments of a few days each, run before any compositor code: start Chromium with GPU disabled, Firefox, a GTK 4 application and a Qt 6 application against a minimal shared-memory-only compositor and record which ones start and open a menu; and attempt a fully static wlroots 0.20 build from `build.zig`. Stage three: the compositor itself, pure Zig if the first experiment passes, on zig-wlroots if it fails and the static build works. The KVM tool comes after stage one or in parallel with stage three as a rest from it, in its smallest form: the CH9329 driver and observation states added to headsight, on the Mac, with the firmware-task benchmark.

Several findings would change this. If agentc or vway gains real users and an independent test within the next couple of months, the compositor becomes a crowded field and the better move is to stay a wrapper (possibly over one of them) and put the effort into the harness. If the stage-one benchmark shows that damage-based settling from outside sway is already right nearly every time, the case for owning the compositor rests on stepping and the single binary alone, which is a weaker case and worth a pause. If Chromium or Electron will not run without GPU buffers, Route C loses its main advantage and Route B becomes the route. If the people you want as users turn out to be hosted-product and evaluation teams, they want virtual machines and isolation, and neither component as scoped here serves them. In the other direction, if your near-term work is on machines where nothing can be installed (a lab bench, a fleet being provisioned, retro hardware), the KVM tool moves first, because the desktop gives nothing there. And if you have no way to keep the KVM tool clearly on the owner-operated side of the line the FBI notice draws, do not publish it.

### How far to trust this report

Weak evidence underlies most of the comparative claims, and the weakness points in a consistent direction. The rival compositors and KVM projects mostly have 0 to 25 stars, the compositors are under three months old, and their feature lists come from their own README files; none was run for this report and none has an independent review. Every performance and memory figure is self-reported by an author or vendor, and the one KVM latency benchmark comes from a competing maker. All line counts and durations for the three routes are the researcher's inference from the size of comparable projects, and the two-to-four-week KVM figure is this report's own. Several facts are secondary reports, including the GNOME and KDE plans and the Ubuntu and Alpine package versions as read from package pages. Whether river runs headless was not verified, the minimum set of interfaces real applications need is inferred, and the claim that X11-only software is a shrinking tail is a judgement, not a count. Detection-evasion techniques for KVM devices were deliberately not researched. The strong evidence is narrower but sufficient for the recommendation: the fixed sleeps in the mainstream products are visible in their source code, the dependency versions and release dates are on the projects' own pages, and the FBI notice is a primary document.

## Conclusion

The two components look like siblings and are not. The KVM tool is a driver problem with a known shape and a political problem attached; the desktop is a compatibility problem with an unknown shape and no politics. That asymmetry is why the order matters more than the choice: the desktop's hard questions (which applications run on a minimal compositor, whether cause-based settling beats observed settling) can only be answered by measurement, and each answer changes what gets built next, while the KVM tool will be the same tool whenever it is started.

Both also converge on one idea that the rivals touch only in passing: the product is the waiting, not the clicking. Sending a key is trivial at every layer, from a compositor call to 8 bytes on a USB wire. Knowing what the machine did in response, when it finished, and whether the picture in hand is current is the part every existing tool either guesses or skips. A shared vocabulary of observation states and wait calls across headterm, headsight, the desktop and the KVM tool would give the later harness one uniform contract to enforce and log, and that contract, more than either component, is the thing nobody else is positioned to offer.
